# Native rendering

Status: **proposed; the Renderer API and a CPU reference renderer exist ([below](#terminal-renderer-api)), and a wgpu implementation of it ([`packages/terminal-renderer-wgpu`](../../packages/terminal-renderer-wgpu/README.md), [below](#wgpu-renderer)) draws the reference's dot-pattern glyphs into an offscreen texture with a bounded glyph atlas, dirty-row batching and no frames while idle; no renderer draws text, is shipped or is wired into the app, and the decisions so far are in [ADR 0001](adr-0001-terminal-runtime.md)**. The shootout also built an Android `Canvas` replay of the layout on Waydroid and libghostty-vt as WebAssembly for the parse stage. The repository contains no Skia code and `MTKView` only in the standalone test host of the [iOS composition PoC](ios-surface-composition-poc.md) (not part of the app) and, apart from the debug-only [Android composition PoC](android-surface-composition-poc.md) and the developer-only [Android native surface host](android-native-surface-host.md) (host and lifecycle, no renderer), no `SurfaceView` or `TextureView` code (searched under `apps/` and `packages/`, excluding vendored sources), and a prototype that is not part of the app, the [Linux composition PoC](linux-surface-composition-poc.md). wgpu is a first candidate, not an assumed winner. Related: [runtime](terminal-runtime.md) · [platform integration](platform-integration.md) · [benchmarks](terminal-benchmarks.md) · [ADR 0001](adr-0001-terminal-runtime.md).

## What must be decided by evidence

1. Whether a native surface can be composed with the Tauri WebView at all on each platform (the **composition gate**).
2. Which renderer is faster and more efficient than an optimized xterm.js on the target devices (the **renderer shootout**, [#1323](https://github.com/mihazs/lazysh/issues/1323)).
3. Whether the input, selection and accessibility story on a native surface reaches parity. A native renderer with broken input or inaccessible content is never shipped.

## Terminal Renderer API

Implemented in [`packages/terminal-runtime`](../../packages/terminal-runtime/README.md) ([#1322](https://github.com/mihazs/lazysh/issues/1322)): the `TerminalRenderer` trait, the shared `Screen` model and a deterministic CPU `ReferenceRenderer`. The trait names no graphics type; a renderer is generic over its own `Surface` (a window handle, an `ANativeWindow`, a `CAMetalLayer`, an image).

| Part | Contract |
| --- | --- |
| Input from the core | `apply(&Frame)`: a full frame or the dirty rows of libghostty-vt's `RenderState`, with the cursor. An incremental frame for a grid the renderer does not hold fails with `NeedsFullFrame`, and the host answers with `TerminalRuntime::snapshot`. |
| Input from the host | `Appearance` (cell metrics in device pixels, font family and fallback list, theme, how bold text is coloured) and `Overlay` (selection, cursor blink phase from one host timer). Changing `Appearance` repaints every row. |
| Drawing and presentation | `draw()` repaints exactly the rows that changed since the last `draw` and returns how many; `present()` shows the result and does nothing when nothing was drawn. Any number of `apply` calls may precede one `draw` per display refresh. `needs_draw()` is true exactly when `draw()` would paint a row, so the host requests a display frame only when it is true and runs no frame loop while it is false; `wants_blink_timer()` is true only while a visible blinking cursor is on a live renderer. |
| Lifecycle | `create(surface, appearance)`, `resize`, `suspend`, `resume`, `destroy`; all but `create` are idempotent. A suspended renderer drops its screen copy and does no work; `resume` is followed by a snapshot. `DeviceLost` has the same recovery. After `destroy` everything but `destroy` and `stats` fails with `Destroyed`. `create` fails with `Unsupported` when the device has no graphics backend the renderer may use (not a loss: `resume` does not help, the host keeps its fallback renderer). |
| Statistics | `stats()` returns cumulative frames drawn and presented, rows and cells drawn, bytes uploaded to the surface, draw and present time, for the benchmarks. |

`Screen` is the half every renderer shares: it applies frames, validates them (a malformed frame is refused and changes nothing), and answers which rows need repainting, including the rows a cursor left and entered, a blink phase change of a blinking cursor, and only the rows whose selected cells changed. GPU and platform renderers keep their own resources but reuse it, so "what changed" is decided once.

`RendererCore` is the third: the lifecycle phases, device loss (including a loss reported from another thread by a GPU callback), the screen copy, "what to draw" (`begin_draw`) and the counters, so every implementation answers the contract the same way and only adds its surface, resources and rasterization. The `forward_to_core!` macro generates the five trait methods that do nothing but forward to it (`apply`, `set_overlay`, `needs_draw`, `wants_blink_timer`, `suspend`, `stats`), which the second implementation (wgpu) showed to be identical for every renderer.

`layout::row_draws` is the other shared half: it turns a row of the `Screen`, the cursor, the selection and the `Appearance` into an ordered list of rectangles and glyph runs in device pixels (cell backgrounds, inverse, faint and hidden colors, underline styles, strike-through, overline, cursor shapes), so "what to paint" is decided once as well. The CPU reference renderer rasterizes the list; a GPU renderer turns it into instances and an atlas, a platform canvas into drawing calls. Renderers then differ only in rasterization, which is what the golden images compare.

**Reference renderer.** It rasterizes the shared layout: cells, wide and combining clusters, default, inverse, faint and hidden colors, underline styles, strike-through, overline, the four cursor shapes and a linear or block selection, using integer arithmetic only, so every host produces the same bytes. It has no typography: each grapheme cluster becomes a 5x7 dot pattern derived from its text, so a wrong cell, width or cluster changes the image without any font. It is not a performance candidate and says nothing about shaping, font fallback, italic, text blink or sub-pixel positioning.

**Golden images.** `packages/terminal-runtime/tests/golden/*.png` (ASCII, ANSI colors, attributes, wide, combining, emoji including a ZWJ family, flag and skin-tone sequence, each cursor shape, cursor on a wide character, linear and block selection) are rendered from real libghostty-vt output and compared pixel for pixel. Separate tests check pixels against the frame instead of a golden, and prove that a sequence of incremental updates ends in the same image as one full repaint.

**Review against the shootout candidates** ([#1323](https://github.com/mihazs/lazysh/issues/1323)). A desk review of how each candidate would plug in; no candidate was built or measured for it.

| Candidate | How it fits | Gap found |
| --- | --- | --- |
| wgpu | Implements the trait directly in Rust. `Surface` wraps a raw window handle, `draw` records instanced quads for the rows `Screen` reports, `present` presents the swapchain, a lost device maps to `DeviceLost`. **Built as a prototype against the trait, which did not change** (`Surface` is the size of an offscreen texture there; `RendererCore` and `layout::row_draws` were enough, and the golden-image oracle was applied to it pixel for pixel, [wgpu measurements](terminal-benchmarks.md#wgpu-prototype-against-the-cpu-reference-renderer-host-gpu-not-a-device)). | `Frame` cells carry an owned `String` each, so a glyph atlas keyed by cluster allocates per cell, which the prototype does (its atlas key is an owned `String` built for every glyph, hit or miss; the cost was not isolated). [#1337](https://github.com/mihazs/lazysh/issues/1337) owns a compact cell format. Not exercised: a window surface, swapchain recreation and a real text pipeline, so `present` and `Surface` are unproven for a window. |
| Native drawing (Skia, Android Canvas) | A Rust implementation is a JNI bridge whose `Surface` is the Java surface; the Kotlin side draws. A replay of `layout::row_draws` on the Android `Canvas` was built and measured (the draws crossed as files, not JNI). Its output was not compared with the reference renderer's pixels (it draws real text); the tuned replay differs from the as-is one in 0 to 0.27 % of pixels. | Rows must cross JNI: the API has no wire format for a frame, which the compact cell format of #1337 should also define. |
| Optimized xterm.js | Does not implement the trait: it parses and renders inside the WebView, so it is a `TerminalAdapter` backend. | None for the API. Its correctness comes from final screen text in the [harness](terminal-benchmarks.md), not from pixels. |
| WASM terminal | The same when it owns parsing and rendering. If only rendering moved to the WebView, `Frame` would have to cross the JavaScript bridge. The parse stage was built and measured (libghostty-vt as WebAssembly, no renderer), not the renderer. | The same wire-format gap. |

The review changed the API in these ways: a statistics record with bytes uploaded, so GPU and surface-copy renderers can be compared on the same counter; a lifecycle in which loss, suspension and recreation recover from core state; and `Frame` now also reports cursor-only changes (see the runtime document). It found no reason to prefer one candidate.

## wgpu renderer

[`packages/terminal-renderer-wgpu`](../../packages/terminal-renderer-wgpu/README.md) ([#1324](https://github.com/mihazs/lazysh/issues/1324)) is the production form of the shootout's wgpu prototype. Its measurements are in [wgpu renderer: idle, atlas and memory](terminal-benchmarks.md#wgpu-renderer-idle-atlas-and-memory-host-gpu-not-a-device).

- **Pipeline.** `layout::row_draws` becomes instances of one instanced-quad pipeline (a solid rectangle or a glyph mask from the atlas, 32 bytes each) drawn into a persistent `Rgba8Unorm` target. A frame submits only the rows that changed: each gets a background instance of the theme color, the cell backgrounds that differ from it are merged into runs, and everything else follows in layout order (no draw leaves its cell, so painting backgrounds first gives the same pixels). A repaint clears first.
- **Glyph atlas.** A fixed-size `R8` texture of slots one cell or two cells wide, with least-recently-used eviction and no compaction (`src/atlas.rs`). Slots used by the frame being built are never evicted; a frame with more distinct glyphs than slots is split into several passes. GPU memory is therefore bounded by the atlas size, the target and a capped instance buffer, whatever passes through. Masks are the reference renderer's dot patterns without fonts and real glyphs with them (the Text bullet below); color glyphs (emoji) live in a second, `RGBA8` atlas of the same kind, so coverage keeps one byte a texel.
- **No idle frames.** `needs_draw()` is false and `draw()` touches nothing for an unchanged screen (no submission, upload or atlas lookup), including when an application rewrites identical cells: `Screen` marks a row dirty only when its cells differ. `GpuStats::submissions` counts `Queue::submit` calls so this is a measured property, not a claim.
- **Backends.** A `Policy` lists backends in order of preference: Vulkan then OpenGL ES on Android and Linux, Metal on Apple, Direct3D 12 then Vulkan on Windows. Within a backend discrete GPUs rank before integrated and virtual ones; CPU adapters are refused unless the policy allows them, because a device keeps xterm.js unless the native renderer can beat it and a software rasterizer cannot. The device is requested with the downlevel (OpenGL ES 3.0) limits raised to what the adapter offers, so the same pipeline runs on the fallback. Metal and Direct3D 12 are compiled in by target but have never run.
- **Device loss.** A lost device is replaced from core state (`resume`, then a snapshot); the device-lost callback carries an epoch so a loss reported by a device that was already replaced does not mark the new one lost.
- **Cursor blink.** The phase is host state; the timer is one for every session. `BlinkClock` derives the phase from a monotonic clock, so all sessions share it, and `next_wake` is the earliest instant any renderer needs, or `None` when no renderer `wants_blink_timer()` (a visible blinking cursor on a live renderer): a steady or hidden cursor, a suspended, lost or destroyed renderer arms no timer. A phase change redraws one row in one pass. `FramePacer` is the same for frames: at most one per display refresh (`set_refresh_hz` when the display changes), none while `needs_draw()` is false.
- **Display scale.** A scale change is a new `Appearance` with `CellMetrics::scaled(n, d)` and a `resize`: the renderer repaints every row from the screen it holds, with no snapshot, rebuilds the atlas for the new cell size (refusing a size the atlas cannot hold with everything unchanged) and draws the same pixels as a renderer created at that scale. Goldens at 2x and 3x pin them.
- **Device loss.** `lose_device()` is the test hook; a reset the renderer was not told about is learned from the device's lost callback or from the errors a destroyed device answers every call with (an out-of-memory or internal error also marks the device lost; a validation error stays a panic, because it is this crate's bug). Recovery is `resume`, a snapshot, a draw: five losses in a row ended in the uninterrupted picture and the driver's resource counts of a new renderer.
- **Window.** A `Target` with a `Window` (the raw display and window handles of `raw-window-handle`) also presents: the adapter must be able to draw on the window, `present` copies the persistent target to the swapchain's next image with one full-surface triangle (vsync, a format without sRGB encoding when the surface offers one, so the theme's bytes arrive unchanged) and a swapchain the platform reports lost marks the device lost, so `resume` builds both again. **No test presents on a window**: the CI hosts that run the renderer have no display, so no test covers this path until a platform surface calls it ([#1327](https://github.com/mihazs/lazysh/issues/1327), [#1331](https://github.com/mihazs/lazysh/issues/1331)).
- **Text: fonts, fallback and grapheme clusters.** ([#1325](https://github.com/mihazs/lazysh/issues/1325); measurements in [text](terminal-benchmarks.md#text-real-fonts-in-the-wgpu-renderer-host-gpu-not-a-device).) The host hands over font bytes (`Target::with_fonts(FontLibrary)`, `WgpuRenderer::set_fonts`): the user's imported fonts live in the WebView's IndexedDB (`fonts.ts`) and system fonts differ per platform, so the renderer never looks a name up on the machine. The app's host gets the imported ones from the page ([#2223](https://github.com/mihazs/lazysh/issues/2223)): `native_terminal_font_import` takes a font's bytes as a raw request with its family (`lazysh-font-<id>-primary` or `-cjk`, the name the page also puts first in the family list) and role in headers, refuses bytes that do not read as a font and keeps the newest four; a look names the families it wants, and the host registers the ones kept (`Look::imported`) before the machine's fonts, restricting a CJK one to the ranges of `fonts.ts`, and reads its fonts again when they change. `Appearance::font_families` orders them: the names it lists first, in order (the preferred family, then the CJK and other fallbacks), unknown names skipped, any other registered family last, so a bundled emoji font stays reachable. `FontLibrary::restrict` gives a family the Unicode ranges the client gives its imported CJK font (`unicode-range` in `fonts.ts`), so Latin text keeps the primary font, and the first unrestricted family sets the cell's font size and baseline. A cluster is drawn into the one or two cells the core gave it (`layout::Glyph::cells`), never the font's advance: the first family with every scalar of the cluster wins (a color face for emoji presentation, `U+FE0F`, keycaps, flags, the pictograph blocks; a text face otherwise; with none, the one covering most, else the primary's missing-glyph box); `swash` shapes the cluster alone (so no ligature or alternate crosses a cell) with its script set (combining marks through GPOS, ZWJ, flag, skin-tone and keycap sequences through GSUB; a variation selector the face does not map is dropped before shaping, as it breaks the keycap ligature otherwise); one em size for every face (the primary's advance of `0` is one cell) on one baseline, so rows align; a cluster wider than its cells is scaled to fit and a narrower one centered; unhinted outlines, CBDT and COLR color. Bold and italic come from the family's own faces (`layout::Glyph::italic` is new) and are synthesized when absent (stroke, 14 degree slant). Presentation is decided by a rule, not Unicode data: a pictograph block scalar takes the color face even where Unicode says text presentation (a thermometer), as long as one is registered. `FontLibrary::system(families)` is the library of a host with no font bytes of its own (`src/system.rs`): it searches the platform's font directories (`/system/fonts` and `/product/fonts` on Android; `/usr/share/fonts`, `/usr/local/share/fonts`, `~/.local/share/fonts` and `~/.fonts` on Linux; none yet on Apple and Windows) reading only each file's table directory, `name` table and `head.macStyle`, and registers, in this order, every installed family the list names with the styles it has, the platform's monospace font under a generic name (`monospace`, `ui-monospace`), a bundled subset of DejaVu Sans Mono (99 kB, Latin, Greek, Cyrillic, arrows, box drawing and blocks; [`fonts/`](../../packages/terminal-renderer-wgpu/fonts/README.md)) so a machine without fonts still draws text, then one CJK and one emoji font. The fonts it chooses are read into memory whole, a CJK collection included; mapping them is left until memory is measured (G15). The fonts a user imported in Preferences live in the WebView's IndexedDB and are not passed to the renderer yet ([#2223](https://github.com/mihazs/lazysh/issues/2223)): with the native engine an imported font is not drawn, an installed family of the same list is.
- **Not done yet.** Any frame presented on a real window, a real-device spot check of text, and any run on Android or Windows hardware.

## Renderer host

`apps/client/src-tauri/src/native_renderer.rs` ([#2215](https://github.com/mihazs/lazysh/issues/2215)), compiled only with the `native-terminal` feature, connects a core `Session` to the wgpu renderer. It holds no platform code and nothing in the app calls it yet: a platform surface ([#1327](https://github.com/mihazs/lazysh/issues/1327) first) hands it a `Target` and the generation it counts.

- **One thread per attached session, asleep until something changes.** The session's `changed` hook rings a `Wake` (one message for a burst). The loop takes the core's frame at once, draws at most once per display refresh (`FramePacer`, 60 Hz) and blocks again: no timer runs for an unchanged screen. A visible blinking cursor wakes it once per phase; every session reads the phase from one process clock (`BlinkClock`), so all cursors blink together. One thread per session, and not one for all, so a present that waits for one window's vsync does not delay another window.
- **Suspend.** `set_active(false)` suspends the renderer and detaches the view from the core, which keeps parsing; `set_active(true)` resumes and draws a snapshot, so what arrived meanwhile is shown.
- **Surface loss.** `lost(generation)` destroys the renderer before it returns (the platform may then take the surface back) and leaves the session alone; a generation that is not the current one changes nothing. `surface(target, generation)` accepts only a newer generation and draws the session from a snapshot, so a late callback cannot bring an old surface back.
- **Device loss.** An error from the renderer resumes it (which rebuilds a lost device) and draws a snapshot; while no device can be built it tries again once a second. A loss on an idle screen is noticed at the next wake (output, a blink phase, a call), not at once.
- **Overlay.** The host draws the selection its session holds (`Session::set_selection`, a range of absolute rows that the app's `terminal_core_select` command sets): with each frame it takes the part inside the viewport, so the highlight stays on its rows while the reader scrolls. `set_composing` draws the text a keyboard is composing: the host writes it, underlined, over the cells from the cursor to the end of its row at most (grapheme clusters, two cells for a wide one, never half a wide character) and puts the cursor after it. The core never holds that text, so while a keyboard composes every frame is a snapshot.
- **Appearance.** `Look` is the user's preferences: the theme (selection colours included), the font family list, the font size and display scale (a cell is 0.6 by 1.2 of the font size and the renderer fits the font to it, one cell being the advance of `0`), and `system_fonts`, with which the host draws with `FontLibrary::system` of the family list (read again when the list changes) and without which glyphs are the reference dot patterns and, through the theme, the cursor's colour. The cursor's shape and blink are the core's, frame by frame: the host cannot tell a cursor no program styled from a steady block a program asked for, so the preferred shape and blink must become the core's default ([#2218](https://github.com/mihazs/lazysh/issues/2218)) and are not applied here.
- **Tests.** In the `native-terminal-bridge` job on Mesa's software Vulkan, on an offscreen target: the pixels of a fed session equal the CPU reference renderer's, an idle session submits nothing, a suspended one draws nothing and catches up, a lost surface and a newer generation give identical pixels, a lost device recovers to identical pixels, a blinking cursor redraws one row per phase, the selection, composing text and the preferences' theme and font size are drawn as the reference draws them, and with `system_fonts` the text is drawn from a font (not the dot patterns, not nothing) and turning it off and on again gives the same pixels each way.

## Renderer candidates

| Candidate | Why considered | Known unknowns (all unmeasured) |
| --- | --- | --- |
| Current xterm.js DOM renderer | Baseline and fallback | CPU, memory, energy, idle activity |
| Optimized xterm.js (WebGL or canvas renderer, binary IPC) | Cheapest possible improvement; no new composition risk | Measured on one desktop Chromium host only ([shootout](terminal-benchmarks.md#renderer-shootout-xtermjs-renderers-1323)): the WebGL addon on hardware GL is on par with DOM for plain output and much cheaper for ANSI-heavy output but has worse W3 frame pacing; the canvas addon is far slower; software GL is unusable. The bold-color seam is refused on both addons. At the phone grid the W3 pacing regression is a cold first-burst stall (7 s, then normal), steady-state CPU on streaming output is higher than DOM, idle with a blinking cursor and multi-session echo are better; a scripted context loss recovered with identical pixels, with the app's handler still unwritten ([phone and context-loss runs](terminal-benchmarks.md#webgl-at-the-phone-viewport-and-its-first-ansi-heavy-burst-1323)). Android devices: unmeasured |
| wgpu (Vulkan on Android and Linux, Metal on Apple, D3D12 on Windows) | One renderer in Rust shared with the core | Measured on one discrete desktop GPU only, with dot-pattern glyphs and no text ([prototype](terminal-benchmarks.md#wgpu-prototype-against-the-cpu-reference-renderer-host-gpu-not-a-device)): a frame is cheap, a first GPU context is not (about 61 MiB resident). Its OpenGL and OpenGL ES backends render the same pixels at about the same median frame cost at the phone grid on that GPU, with a worse tail and about 65 MiB for the first context ([measurement](terminal-benchmarks.md#wgpu-on-its-opengl-and-opengl-es-backends-against-vulkan-same-host-gpu-not-a-device)). Unmeasured: Android driver quality, binary size, idle wakeups, shaping and font fallback effort |
| Native drawing (Skia or Canvas, especially Android) | Platform-tuned text drawing and fonts | Replay of the shared layout with the Android `Canvas` (Skia) on Waydroid, whose GPU is a desktop part ([measurement](terminal-benchmarks.md#android-canvas-drawing-of-the-shared-layout-waydroid-not-a-device)): every frame fit in 16.7 ms and the cost was the number of Canvas calls, not the GPU. Unmeasured: any phone, the app's fonts, per-row display lists, Rust-to-Kotlin transport, cross-platform reuse |
| WASM terminal in the WebView | Keeps DOM composition and removes JS parsing | Parse stage only, on one V8 in Node ([measurement](terminal-benchmarks.md#webassembly-vt-versus-xtermjs-parse-only-host-microbenchmark-not-a-candidate)): libghostty-vt built to WebAssembly from the vendored source parsed 1.3 to 5.8 times faster than xterm.js's parser. Cold start in Node (fresh process, 14,800 bytes parsed): 8 ms against 21 to 22 ms for xterm.js headless, and 4.7 MiB more resident ([measurement](terminal-benchmarks.md#wasm-terminal-cold-start-node-fresh-process-per-sample)). Unmeasured: a renderer, the JS bridge that carries every byte and dirty row, Chromium and Android WebViews, SIMD, startup on a phone |

Decision rule: choose per platform by validated responsiveness, energy, memory and correctness; ship only the winner; if none beats the xterm.js fallback on a device, that device keeps xterm.js. Prototypes are not shipped.

## Composition gate

Required before any production surface work. Each item is recorded pass or fail with evidence (device, OS, WebView version):

| Gate | What is checked |
| --- | --- |
| Placement | A surface tracks a DOM anchor through scroll, resize and layout changes. |
| Overlap | React overlays, menus, the command palette, the toolbar and selection handles draw correctly over or around the surface. |
| Focus handoff | Focus moves between WebView inputs and the terminal without losing the keyboard state. |
| Selection | Handles and the selection toolbar work (they are DOM today: `TerminalSelectionTools.tsx`). |
| Resize | Keyboard show or hide, orientation, foldables and insets resize the surface and the PTY once. |
| Destroy and recreate | Surface loss and activity recreation rebuild the view from core state. |
| Accessibility feasibility | A route to screen-reader content exists ([accessibility](#accessibility)). |

Android emulator results: [Android surface composition PoC](android-surface-composition-poc.md). Linux results (Wayland passes on one compositor and GPU, X11 fails the overlap item): [Linux surface composition PoC](linux-surface-composition-poc.md). iOS results (an `MTKView` below the transparent `WKWebView` passes on the hosted simulator): [iOS surface composition PoC](ios-surface-composition-poc.md). Proof-of-concept issues: Android [#1310](https://github.com/mihazs/lazysh/issues/1310), iOS [#1311](https://github.com/mihazs/lazysh/issues/1311). Windows results (a Direct3D 12 child window below the transparent WebView2 passes on a hosted runner): [Windows surface composition probe](windows-surface-composition-poc.md). macOS results (an `NSView` hosting a `CAMetalLayer` below the transparent `WKWebView` passes at 1x on the hosted runner, scale 2 not measured): [macOS surface composition PoC](macos-surface-composition-poc.md). The strategies read from the shipped windowing stack are in [surface strategies](windows-macos-ios-surface-strategies.md); the macOS surface itself follows in [#1333](https://github.com/mihazs/lazysh/issues/1333), the rest of the Windows work is in [#1332](https://github.com/mihazs/lazysh/issues/1332), and the iOS surface follows the [iOS PoC](ios-surface-composition-poc.md) in [#1330](https://github.com/mihazs/lazysh/issues/1330). A platform that fails its gate keeps xterm.js, or uses the documented alternative.

Android strategies in order of trial: `SurfaceView` first (lowest compositing cost where it works; z-order and clipping against a WebView are the risk), then `TextureView` if clipping, z-order or transitions demand it. What the WebView host does today: `MainActivity` extends `TauriActivity`, registers Kotlin plugins in `onWebViewCreate`, and applies system-bar, cutout and IME insets as padding on the content view so the WebView itself is resized.

## Frame scheduling

- Event-driven: a frame is requested only when core state, the cursor blink phase, selection or the viewport changed. No fixed 60 or 120 Hz loop while idle.
- Coalescing: output bursts produce at most one frame per display refresh; the core continues parsing between frames.
- Inactive sessions do not render; a hidden surface releases or parks GPU work.
- Cursor blink uses a single coalesced timer and is skipped entirely when blink is off or the surface is hidden (`BlinkClock` and `wants_blink_timer`, [above](#wgpu-renderer); [measurement](terminal-benchmarks.md#cursor-blink-display-scale-and-device-loss-host-gpu-not-a-device)).
- Acceptance: zero frames submitted while the screen is unchanged and blink is off ([#1324](https://github.com/mihazs/lazysh/issues/1324)). Met by the wgpu renderer for an unchanged screen: `needs_draw()` is the host's question, `GpuStats::submissions` the proof ([measurement](terminal-benchmarks.md#wgpu-renderer-idle-atlas-and-memory-host-gpu-not-a-device)); the blink timer is [#1326](https://github.com/mihazs/lazysh/issues/1326).

## Glyph atlas, shaping and layout

- Dirty-row and cell-run tracking, instanced quads, a glyph atlas with bounded size and eviction (done in the wgpu renderer, [above](#wgpu-renderer)), minimal uploads, resources shared across sessions where fonts match ([#1337](https://github.com/mihazs/lazysh/issues/1337)).
- Cell widths come from the core (`unicode_grapheme_width`); shaping must not move glyphs off the grid for CJK, ZWJ emoji and combining marks ([#1325](https://github.com/mihazs/lazysh/issues/1325)). The user's font and CJK fallback settings (`fonts.ts`, [font downloads](../font-downloads.md)) must be honoured. Done in the wgpu renderer ([above](#wgpu-renderer)): clusters stay in their cells, the font list orders the faces, and the tests are `packages/terminal-renderer-wgpu/tests/text.rs` and its goldens; not yet on a device.
- Cursor styles, blink, selection highlight, high-DPI scale changes and device-loss recovery are covered by [#1326](https://github.com/mihazs/lazysh/issues/1326) for the dot-pattern glyphs the reference renderer draws: tested in `packages/terminal-renderer-wgpu/tests/lifecycle.rs` ([above](#wgpu-renderer)). With real fonts they are the same tests again.

Capability must be detected on real hardware (driver blocklists, surface creation, a short render self-test), not inferred from the OS version ([#1336](https://github.com/mihazs/lazysh/issues/1336)). No claim is made here about which backends work on which devices.

## Input and IME

The highest-risk area. Today input depends on xterm's hidden textarea and the pinned IME layer (`terminalIme.ts`). A native surface needs either a hidden DOM editor kept alongside the surface or a native input connection. The decision is made in the Android PoC and validated against SwiftKey and Gboard behaviour (#1215), the `terminal-ime` and `terminal-swiftkey` scenarios, and the owned IME test service in the Android instrumentation sources. Required: no duplicate or corrupt commits, hardware keyboards, Shift+Enter (#805), toolbar Enter (#1043), touch scrolling (#938) and selection handles. Tracked in [#1328](https://github.com/mihazs/lazysh/issues/1328). For Android, a native input connection (the keyboard's editor owned by the app, with composition, commit and hardware-key handling) is implemented and tested in developer builds but not connected to a surface or the core: [Android native input](android-native-input.md).

## Accessibility

xterm.js offers `screenReaderMode` (wired to `preferences.screenReader`). A GPU surface has no DOM, so a native backend that wants a screen reader to reach its content mirrors rows into a hidden DOM region. The decision (the hidden live region over a virtual accessibility tree, because the WebView above or beside the surface already hands the DOM to TalkBack, VoiceOver, Narrator, NVDA and Orca) and its limits:

- `terminalScreenReader.ts` builds the mirror from `readRows` of the visible viewport only, never from cells. It is a visually hidden `role="list"` of the visible rows (the cursor row is `aria-current="location"`) and a polite `role="log"` of announcements.
- Cost is bounded: output events inside a 150 ms window cost one read of the viewport; announcements are at least 1 s apart, at most 8 lines (more than that is one "N lines changed" line, which is also what a full-screen redraw becomes), the log keeps the last 20, and a selection is spoken cut at 200 characters.
- What is spoken is the diff of rows, not the screen: lines that scrolled in, the characters appended to an edited row, the row under the cursor when only the cursor moved (a menu), and a selection. Nothing is spoken while the reader looks at history. A new row identical to one still on screen counts as unchanged (the text cannot tell them apart); per-row change flags from the core would remove that limit.
- A backend declares the `accessibility` capability only when it mounts this mirror and the mirror passed its test on the platform. Backend selection requires `accessibility` while the screen-reader preference is on (`screenReaderRequirements`), so a native backend without it is refused, xterm.js is used and the registry records `lacks accessibility`. On Android the requirement also holds while the system reports a screen reader (`screen_reader_active`: touch exploration or a spoken or braille accessibility service, [#1329](https://github.com/mihazs/lazysh/issues/1329)), whatever the preference says; the shipped policy there is the refusal, not the mirror, and a session already open keeps its engine.
- `TerminalPane` mounts the mirror in the terminal container of a native session while the screen-reader preference is on (a preference turned on after the session started), and removes it when the preference goes off or the pane ends. The native adapter reports `accessibility` only while a mirror is mounted (`screenReaderMirrored`); the backend's registration still declares it `false`, so a session that starts with the preference on is still refused native and gets xterm.js. The platform surface itself stays out of the accessibility tree (on Android the host view is `IMPORTANT_FOR_ACCESSIBILITY_NO`).

Not verified: TalkBack, VoiceOver, Narrator, NVDA or Orca reading the mirror. The unit tests prove the DOM and the announcement bounds, not what a screen reader says. Tracked in [#1329](https://github.com/mihazs/lazysh/issues/1329) and [#1335](https://github.com/mihazs/lazysh/issues/1335).

## Rejected or deferred alternatives

- **Port the xterm DOM renderer to Rust**: no benefit; the cost is parsing and DOM updates, which this design moves out of JavaScript only if measured.
- **A second VT engine for rendering**: duplicates state; rejected by the one-authoritative-state principle.
- **Immediate-mode redraw of the whole grid each frame**: conflicts with the idle requirement.
- **Choosing wgpu first**: rejected by the requirement to decide on measurements.

## Unresolved questions

- Can a `SurfaceView` be z-ordered with a transparent hole in the Tauri WebView, or is `TextureView` required? On an API 36 emulator a `SurfaceView` below a transparent WebView works and keeps DOM overlays on top, and `TextureView` works too ([result](android-surface-composition-poc.md)). Still open: the real, currently opaque page, and a physical device.
- Does iOS allow a Metal view at the required z-order without interfering with WKWebView scrolling and hit testing? On the hosted simulator an `MTKView` below a transparent `WKWebView` keeps the DOM overlays on top, leaves scrolling and hit testing to the web view, and resizes once per keyboard transition ([result](ios-surface-composition-poc.md)). Still open: a device, the real Tauri window and the opaque page, other scales and iPad.
- Can an `NSView` with a `CAMetalLayer` sit below the transparent `WKWebView` in wry's `WryWebViewParent`? On the hosted macOS runner at 1x it shows through at the DOM anchor with 0 px error, keeps DOM overlays on top, follows an anchor change, a resize and a recreate, and leaves the pointer hit test and keyboard focus to the web view, but only because the web view is built transparent with wry's private `drawsBackground` key ([result](macos-surface-composition-poc.md)). Still open: scale 2 (the runner has no 2x display), the real Tauri window and opaque page, real input, and the Mac App Store.
- How are Wayland subsurfaces handled by the WebKitGTK window Tauri uses? A `wl_subsurface` placed below the toplevel, under a transparent window and web view, composes correctly on KWin 6.8.2 with a wgpu Vulkan swapchain on an AMD GPU, and an X11 child window does not (it covers DOM overlays) ([result](linux-surface-composition-poc.md)). Still open: other compositors and GPUs, fractional scale, real input, and the real page.
