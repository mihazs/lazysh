# Linux native surface host

Status: **host and renderer, in builds with the `native-terminal` feature, which no release enables**. A session that has a native core is drawn on its surface by the renderer host; the page captures Linux keyboard input in a DOM textarea. Linux IME and assistive-technology parity still require validation. Linux releases still default to xterm.js. It is the surface host of [#1331](https://github.com/mihazs/lazysh/issues/1331) (epic [#1302](https://github.com/mihazs/lazysh/issues/1302)) and follows the strategy the [composition proof of concept](linux-surface-composition-poc.md) recommended: a `wl_subsurface` below a transparent toplevel and web view on Wayland, and xterm.js on X11 and Xwayland. Related: [Android host](android-native-surface-host.md) · [native rendering](native-rendering.md) · [terminal adapter](terminal-adapter.md) · [migration plan](terminal-migration-plan.md).

## What exists

| Piece | Where | Role |
| --- | --- | --- |
| `native_terminal_surface_place`, `_remove`, `_state` | `apps/client/src-tauri/src/native_terminal_surface.rs` | The Android commands, with the same arguments, validation and locked-app rule. On Linux with the feature they run the host on the GTK main thread. Every other build answers that it has no surface. |
| The host | `apps/client/src-tauri/src/native_terminal_surface/linux.rs` | One `wl_subsurface` per session on GDK's own Wayland connection, a child of the toplevel `wl_surface`, placed below it, desynchronised, with an empty input region and a `wl_shm` buffer of the pane background. |
| The renderer | `Pane::draw` in `linux.rs`, `native_renderer.rs` | When the session has a native core (`Core::drawing`), the pane hands GDK's `wl_display` and the subsurface's `wl_surface` to the [renderer host](native-rendering.md) as raw Wayland handles (`Window::wayland`): a wgpu swapchain on Vulkan, then GLES, sized in device pixels, resized with the anchor, destroyed before the surface. The session's `changed` hook rings the host's wake as well as the page's doorbell. The page's preferences reach it through `native_terminal_surface_look` (`Pane::relook`, [the look](android-native-surface-host.md#the-look)); a session that never received one is drawn with the default look. The `wl_shm` fill stays for a surface without a core or a device that cannot draw. A set `LAZYSH_NATIVE_TERMINAL_SOFTWARE_GPU` lets the host use a CPU rasterizer (the CI runner's lavapipe); the probe never does. |
| The transparent window | `build_unspawned_windows` in `lib.rs` | With the feature, the window and its web view are created transparent. The page still paints its own backgrounds everywhere except above a native pane ([the pane](android-native-surface-host.md#the-pane)). Without the feature the window is what it was. |
| The display check | `surface()` in `terminal_core.rs` | `native_terminal_probe` reads the GDK display type recorded when the window was built. Anything but `GdkWaylandDisplay` is refused before the GPU is asked, with the display named in the reason. |

The page side is the Android one: `terminalSurfaceAnchor.ts` sends the same three commands, so nothing in the client changed.

## Contract

- **Position.** The anchor is the element's rectangle in CSS pixels with the page's `devicePixelRatio`. The host turns it into logical pixels of the toplevel (CSS pixels times the ratio, divided by GTK's scale) and adds the web view's offset inside the toplevel, which GTK's own title bar and shadow make non-zero. It places every surface again when the web view's allocation or the window's scale changes, without the page asking.
- **Size.** The buffer is the logical size times GTK's integer scale, with `wl_surface.set_buffer_scale`. `_state` and `_place` report it in device pixels. GTK 3 has no fractional scale: a fractional output scale reaches the host rounded up, as it does the page.
- **Generation** is 1 for a placed session and 0 otherwise: a session has one surface from `place` to `remove`.
- **Removal.** `remove` destroys the subsurface. Removing a session that is not there is not an error, and is allowed while the app is locked.
- **X11 and Xwayland.** `place` is refused with a reason that names the display, `state` answers unplaced, and the probe refuses native, so the registry keeps xterm.js and shows why. The window is on X11 when its GDK display is, whatever the session type says.
- **Limits.** At most 64 surfaces. A window that is unmapped loses its surfaces and the page is not told (the app never hides its window).

## Local hardware and production-page results

- The native debug app on `09c24f72` passed 13 composition fixture assertions at scale 1 in a private virtual KWin session on a Radeon RX 5500 XT using RADV Vulkan. With software fallback disabled, compositor readback verified placement, DOM overlap, anchor movement, removal, recreation, and four colored cells from a real local PTY. This KWin run did not drive compositor resize. [Hardware run](https://github.com/mihazs/lazysh/issues/1331#issuecomment-7159467435)
- The debug app loaded the production terminal page from Vite. On the native engine, a mouse click focused the DOM terminal editor, and WebDriver keystrokes reached a real local shell. Both engines pasted the same Unicode text from the Wayland clipboard into the shell. Both preserved the clipboard before OSC 52 consent. After consent, WebKit reported success while the compositor clipboard retained the baseline for both engines in this WebDriver setup. [Keyboard](https://github.com/mihazs/lazysh/issues/1334#issuecomment-7159560141) · [Paste](https://github.com/mihazs/lazysh/issues/1334#issuecomment-7159576113) · [Copy](https://github.com/mihazs/lazysh/issues/1334#issuecomment-7159624063)
- A mouse drag across real shell output selected the same eight-letter token in both engines and sent it to WebKit's clipboard API. The endpoint differed between engines. [Mouse selection](https://github.com/mihazs/lazysh/issues/1334#issuecomment-7159898496)
- On isolated Xvfb, requesting native in the production page selected xterm.js. The native probe named `GdkX11Display`, and keyboard input reached the real local PTY through the fallback. The same fallback worked on Xwayland inside KWin with `XDG_SESSION_TYPE=wayland`. [Xvfb](https://github.com/mihazs/lazysh/issues/1331#issuecomment-7159723802) · [Xwayland](https://github.com/mihazs/lazysh/issues/1331#issuecomment-7159748550)
- A production-page window resize under KWin reduced the native pane from 900 × 573 to 640 × 397 CSS pixels. The real shell reported a PTY grid change from 112 × 33 to 80 × 23, and compositor screenshots showed the shell output inside the resized pane. [Resize run](https://github.com/mihazs/lazysh/issues/1331#issuecomment-7159804415)
- With native available and explicitly requested on KWin, the screen-reader preference selected xterm.js for a new session. Its DOM accessibility tree contained output computed by a real local shell. [Accessibility fallback run](https://github.com/mihazs/lazysh/issues/1335#issuecomment-7159788334)
- With one focused local PTY and a 900 × 573 CSS-pixel pane, median idle app-process-tree CPU across three 10-second measurements was 2.10% of one logical CPU for native (2.00–2.20%) and 2.30% for xterm.js (2.30–2.40%). These debug-build samples exclude compositor CPU and GPU activity. [Idle CPU](https://github.com/mihazs/lazysh/issues/1331#issuecomment-7159677053)
- Over five runs per engine with 120 alternating-color PTY updates at about 60 Hz, median run p50/p95 Wayland commit gaps were 16.73/16.93 ms for the native terminal subsurface and 16.74/17.30 ms for the xterm.js window. The xterm.js window can also commit UI changes. These client-side traces measure buffer submission cadence. Compositor presentation, render duration and dropped frames remain unmeasured. [Wayland timing](https://github.com/mihazs/lazysh/issues/1331#issuecomment-7159866485)
- In niri 26.04 nested under KWin at 150% scaling, compositor screenshots showed the production command palette above the native terminal. The palette accepted text and, after dismissal, keyboard input reached the real local shell again. A compositor-driven resize reduced the native pane from 570 × 227 to 420 × 120 CSS pixels and the PTY grid from 67 × 13 to 49 × 7. [Fractional-scale run](https://github.com/mihazs/lazysh/issues/1331#issuecomment-7161554533)

- On isolated Mutter 51.1 with a 1280 × 800 virtual monitor and the amdgpu render node, the production command palette accepted input over the native pane. The same local shell accepted keyboard input after dismissal and its PTY grid changed from 122 × 27 to 80 × 19 after a resize. [Mutter input and resize](https://github.com/mihazs/lazysh/issues/1331#issuecomment-7161669231)
- In two matched runs per engine on that virtual monitor, the same 120-update PTY workload gave p95 gaps of 16.751 and 16.753 ms between Mutter presentation events for native and 16.751 and 18.021 ms for xterm.js. The p95 compositor CPU paint spans were 0.045 and 0.047 ms for native and 0.031 and 0.033 ms for xterm.js. Presentation events cover the entire virtual output. Physical scanout, GPU draw time and one-to-one delivery of PTY updates remain unmeasured. [Matched runs](https://github.com/mihazs/lazysh/issues/1331#issuecomment-7161717167)

Gate G19 stays open for Linux. Remaining checks include Mutter pixel readback, GPU draw time, physical display presentation, input parity, automatic assistive-technology detection and external screen-reader behavior.
