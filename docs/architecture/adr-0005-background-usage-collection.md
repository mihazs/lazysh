# ADR 0005: opt-in background usage collection and a host switch for account quota reads

- Status: **Accepted** as the design, 2026-11-14, and delivered by [#1823](https://github.com/mihazs/lazysh/pull/1823) (the policy file and quota switch, the collector and its timers, the app view); that pull request says what shipped and what was not exercised. The maintainer's standing instruction (implement every issue of the project with conservative defaults) made the choices below without a separate review; the maintainer can amend any of them.
- Decision makers: repository maintainer. Tracking: [#1588](https://github.com/mihazs/lazysh/issues/1588), slice 4 of [#18](https://github.com/mihazs/lazysh/issues/18).
- Related: [recorded token usage](../usage.md) · [AI account usage](../ai-account-usage.md) · [host companion settings](../companion-settings.md) · [settings reference](../reference/companion-settings.md) · [ADR 0003](adr-0003-host-side-companion-update.md) (the same timer and state-file conventions).

## Default policy amendment

[#2532](https://github.com/mihazs/lazysh/issues/2532) changes the absent-file default to `collectorEnabled: true`. Managed companion setup provisions a missing user timer when both collection and quota reads are enabled. Saved policy values still apply. A manual installation can provision the timer with `lazysh-agent usage-collector ensure`. The decisions below record the original rollout.

## Context

What the code does today (read at `origin/main` 6529320b):

- `lazysh-agent usage` reads **recorded transcript counters** from one transcript the user selected. It reads no credential and makes no request. The host switch `recordedUsageEnabled` in `settings.json` gates it.
- `lazysh-agent account-usage` reads **live provider quota** (`packages/account-usage`): it uses the host's own provider credentials, may start an installed `ai-usagebar` or the built-in collectors, and makes outbound requests to each configured provider (deadlines: 6 s external CLI, 18 s built-in). **No host switch governs it.** It answers `{schemaVersion, state, source, report}`.
- The app asks for the quota every five minutes **while the Usage or AI account usage view is visible** (`apps/client/src/useAccountUsage.ts`). Nothing runs while the app is closed, so a refresh shows no history and "stale" is the only honest label for an old counter.
- `settings.json` is read with `deny_unknown_fields`, so a new key there would make an older companion on the same state directory refuse its settings. Every later setting therefore lives in its own file: `auto-update.json` ([ADR 0003](adr-0003-host-side-companion-update.md#auto-update)) and slice 2's `host-features.json` ([#1586](https://github.com/mihazs/lazysh/issues/1586), not on `main` when this was written).
- Companion state is a directory of small owner-only files with a revision and a lock file each, read without creating anything and replaced atomically (`apps/agent/src/private_json.rs`).

The requirement ([#18](https://github.com/mihazs/lazysh/issues/18)): opt-in background collection, default off, with missing data shown as unknown, no invented percentages, old counters labelled stale and credentials never scraped or exported. The account quota read must be forbiddable by a host.

## Decision

1. **One new strict file, `usage-collection.json`, holds the policy.** It sits beside `settings.json`, has its own revision, its own lock (`usage-collection.lock`), a 4 KiB limit, mode 0600 and an atomic replace, exactly like `settings.json`. Absent means the defaults below and creating nothing. Fields: `schemaVersion` (1), `revision`, `accountQuotaEnabled` (default `true`), `collectorEnabled` (default `false`) and `collectorIntervalMinutes` (default 30, from 5 to 1440). It does not use `settings.json` (older companions would refuse it) and not `host-features.json` (slice 2 is a different change that may merge before or after this one; the file here is independent, so the slices merge in either order and an older companion ignores it).
2. **`accountQuotaEnabled` governs the account quota read, and a disabled read reports a reason, never a number.** Default `true`, so no existing host changes. With it `false`, `lazysh-agent account-usage` prints `{"schemaVersion":1,"state":"disabled","source":null,"report":null}` and exits 0, **before** it opens a credential file, starts a process or makes a request. The new state `disabled` is "unknown, forbidden by the host": it carries no report, so the app shows no percentage and never zero. The collector honours the same switch. The switch is changed with `lazysh-agent usage-collection update --expected-revision R --account-quota-enabled true|false` (a stale revision is `SettingsConflict`, a busy lock `SettingsBusy`, as for `settings update`) and read with `usage-collection show`.
   - *Scope of the guarantee.* It binds the **host companion**: every remote host, and anything else that runs `lazysh-agent account-usage`. A companion older than this change ignores the switch (the app can tell: `usage-collection` is an unknown subcommand, exit 2). The desktop app's own read of its **local** machine does not go through the companion and is not governed; the machine's user is the host's owner there. The documentation says so.
3. **The collector is a scheduled, one-shot command, not a daemon.** `lazysh-agent usage-collector enable [--interval-minutes N]`, `disable`, `status [--limit N]` and `run`.
   - `enable` first installs the OS timer (decision 5); only if that succeeds does it record `collectorEnabled: true` and the interval in the policy file, under the policy lock. A timer that cannot be installed leaves the policy as it was.
   - `disable` records `collectorEnabled: false`, then removes the timer. Nothing is written while the collector is off, so recorded samples stay on disk unchanged (not even pruned) until the user deletes `usage-samples.json` (the documented path) or enables the collector again, whose next write prunes them by the normal bounds.
   - `run` is what the timer executes. It reads the policy first: when the collector is off, it exits 0 having read nothing else and written nothing, so a timer that outlived a `disable` is harmless. When it is on and the last run is younger than the interval, it exits 0 and writes nothing (the timer ticks more often than the interval, decision 5). When a run is due it reads the quota once with the same code as `account-usage` and the same deadlines, appends one sample and rewrites the sample file. It takes the policy lock again **before the write** and re-reads the policy, so a run that finished after `disable` returned writes nothing.
   - Expected outcomes are recorded and exit 0 (`recorded`, `skipped` with `accountQuotaDisabled`, `unavailable` with the quota response's own state, for example `timeout`), so the OS timer does not report a failure for a host that is offline. A malformed policy or sample file exits 1 and is never repaired: the sample file is disposable (delete it to restart), the policy file is not.
4. **A sample is a bounded projection of the quota report, with a timestamp from the host's clock, and exists only for a read that produced a report.** It contains `recordedAt` (RFC 3339 UTC), the report's `source`, `truncated`, and per account entry: `id`, `name`, `status`, `stale`, `fetchedAt` and the **metric rows** (`label`, `percent`, `reading` (`used` or `left`, what the percent measures), `resetAt`, `windowSeconds`, nothing else). A read that produced no report (offline, timed out, forbidden) records only the **last run** (`at`, `outcome`, optional `reason`). The sample does not contain plan names, balance rows, free text, credentials, prompts, transcript text, session titles or paths: the report shape already excludes them ([AI account usage](../ai-account-usage.md)) and the projection drops everything not listed. At most 32 entries and 16 rows per entry are kept, with `truncated: true` when more existed. A percentage the provider did not report is absent, not zero.
   - **Bounds.** `usage-samples.json` keeps at most 1000 samples, none older than 7 days, and at most 1 MiB; the oldest sample goes first. The file also holds `lastRun` (`at`, `outcome`, optional `reason`), so a host that is offline or forbidden shows a run without a sample. At the 5-minute minimum interval the size bound, not 7 days, limits the history; at the default 30 minutes 7 days is 336 samples. The bounds are fixed in this version; nothing user-set can grow the file.
   - **The existing recorded-usage shape.** The issue asks for "the existing recorded-usage shape". The transcript counters of `usage` need a transcript the user chose, and an unattended collector choosing transcripts would widen the privacy boundary that [recorded token usage](../usage.md) states. This version records the quota report in the same style (nullable fields, timestamps, `stale`) and leaves background transcript counters as a separate follow-up that needs its own boundary decision.
5. **The scheduler is a user-level OS timer that only wakes `run`.** No sudo, no elevation, no resident process; the templates are fixed text around the absolute path of the running executable and nothing else, so no setting or user text reaches a unit, a plist or a task.
   | Host | Mechanism | Files |
   | --- | --- | --- |
   | Linux | `systemd --user`, `OnCalendar=*:0/5` with `Persistent=true` | `~/.config/systemd/user/lazysh-usage-collector.{service,timer}` |
   | macOS | launchd agent of the login session, `StartInterval` 300 | `~/Library/LaunchAgents/app.lazysh.usage-collector.plist` |
   | Windows | Scheduled Task of the current user, repeating every 5 minutes, `StartWhenAvailable` | task `lazysh-usage-collector` |
   - The timer **ticks every 5 minutes; `run` enforces the user's interval** from the last run time, less one minute of slack (a run starts a moment after its tick, so a 5-minute interval would otherwise become 10), which rounds an interval up to a multiple of 5 minutes. Changing the interval or the switch never touches the timer, and the shortest interval is the tick.
   - **When a timer can run.** `systemd --user` runs only while the account has a session unless the owner enables lingering (`loginctl enable-linger`), which `enable` never does because it changes system state; `status` reports `linger` so the owner can see why nothing was recorded. launchd needs the user's GUI login domain, so an account reached only over SSH exits 41. A Windows task runs while the user is logged on (interactive token, no stored password).
   - Every file or task carries the marker `lazysh-agent-managed: usage-collector`. `disable` removes only what carries it; a file without the marker, or a link, is never replaced or removed.
   - `enable` exits 41 when the account cannot have a timer (no user service manager or login session) and changes nothing, and 42 when the system refuses it, with the files put back as they were (the same meaning as ADR 0003's `timerUnsupported` and `timerFailed`). `status` reads the real OS state back and reports `timer.state` as `absent`, `installed` or `drift` (installed but not matching the template or the policy), `unsupported` where the host has no way to hold one.
6. **Suspend, shutdown and offline.** Nothing runs while the host is off or suspended and no sample is invented for the gap. The first tick after a resume (systemd `Persistent=true` and launchd and Task Scheduler's catch-up) finds the interval elapsed and records **one** sample; there is no burst of back-filled samples. The gap stays visible: the app shows the age of every sample from its own `recordedAt`, never an interpolated value. A tick while offline records the `unavailable` run and no sample. A sample is never marked fresh because it exists: `stale` and `fetchedAt` of the provider's entry travel with it, and the app ages `recordedAt` against the host's `observedAt` (returned by `status`) so a skewed phone clock cannot rejuvenate it.
7. **The privacy boundary.** The collector adds **one** thing: the host contacts each configured provider on the user's interval while no lazysh app is open, using the credentials the quota read already uses. That is why it is off by default, why it has a 5-minute floor (provider rate limits and no hammering) and why the documentation names it before the enable command. It reads no transcript, writes nothing outside the state directory and its timer files, sends nothing anywhere itself and exports nothing: the app receives the samples only through `usage-collector status` over the user's own SSH connection. It stores no credential, only what the quota report already shows the app.
8. **Restart semantics.** No process is resident, so there is nothing to restart. `usage-collector enable|disable` and `usage-collection update` apply from the next tick or the next `account-usage` call. A quota read already in flight finishes (a collector run never cancels its own read), but a run that was in flight when `disable` returned writes nothing (decision 3). Updating the companion does not change the timer: the unit holds the absolute path of the managed executable, which an atomic replace keeps valid.
9. **What the app shows (a later slice).** The collector's state (on or off, interval, timer present or drifted), its last run (time and outcome) and the age of every sample, from `status`; the `disabled` quota state as "turned off on this host", with no percentage; unknown and stale labels unchanged. A companion without `usage-collector` shows the existing "update the companion" message.

## Alternatives considered

- **Collect while the app is open only** (today): cannot show consumption between sessions.
- **A resident collector daemon**: the companion has no resident server today; a daemon needs its own supervision and survives badly across updates. A timer needs neither.
- **Default on**: it uses stored credentials and contacts providers while nobody looks. It needs an explicit opt-in.
- **A switch inside `settings.json`**: older companions refuse unknown keys.
- **A switch inside `host-features.json`**: couples this change to slice 2's merge order for no gain.
- **Record transcript counters unattended**: see decision 4; deferred, not rejected.
- **SQLite for the samples**: a bounded JSON file of at most 1 MiB is read whole in milliseconds, has no schema migration and no extra crash recovery.
- **A timer period equal to the user's interval**: every interval change would rewrite and reload the timer on all three platforms. A fixed tick plus `run` deciding is the same cost and one fewer thing that can drift.

## Delivery

1. This ADR (docs only).
2. `usage-collection.json`, `usage-collection show|update`, the `disabled` quota state and its strings in every locale, and the documentation of the switch.
3. `usage-collector enable|disable|status|run`, the sample file, the three timer templates and the documentation of the privacy boundary and restart semantics.
4. The app: the collector's state, last run and sample ages in the Usage view, in every locale. The switches stay on the host (`usage-collector enable|disable`, `usage-collection update`), as `auto-update` does; the app never changes them, and an in-app control would be a separate, explicit decision.

Test seam: in debug builds only, `LAZYSH_USAGE_TIMER_BACKEND_FOR_TESTS` names the backend (`systemd`, `launchd`, `schtasks`) so that each can be driven on one machine against stand-in tools; release builds ignore it.

Evidence each slice must attach: Rust tests with an injected clock and a temporary state directory (collector), a CLI test of the disabled reason (switch), the timer files executed or validated where the runner allows (`systemd-analyze verify` against a stand-in `systemctl`, XML parsing of the launchd and Task Scheduler documents) and an explicit statement of what no runner could exercise (a real launchd and Task Scheduler, a real suspend).
