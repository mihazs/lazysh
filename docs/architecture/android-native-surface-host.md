# Android native surface host

Status: **host, lifecycle and a JNI renderer client, open to release builds only through an explicit Native choice**. The renderer client is built but has not yet drawn a core on a device (see [the renderer client](#the-renderer-client)); no input, IME or accessibility reaches it, and the pane that would place it is mounted only by tests: no backend registration gives a session a native terminal yet. It is the first slice of [#1327](https://github.com/mihazs/lazysh/issues/1327) (epic [#1302](https://github.com/mihazs/lazysh/issues/1302)) and follows the strategy the [composition proof of concept](android-surface-composition-poc.md) recommended: a `SurfaceView` stacked below a transparent WebView. Related: [native rendering](native-rendering.md) · [runtime](terminal-runtime.md) · [platform integration](platform-integration.md) · [migration plan](terminal-migration-plan.md).

## What exists

| Piece | Where | Role |
| --- | --- | --- |
| `TerminalSurfaces`, `SurfaceHost`, `BackgroundPainter` | `gen/android/app/src/main/java/app/lazysh/client/TerminalSurfaces.kt` | A process-owned registry of sessions. Each session has one `SurfaceView` at index 0 of the content frame (so the WebView paints over it), placed from a DOM anchor, and a client that draws on it. |
| `SurfaceLifecycle`, `SurfaceClient`, `SurfaceAnchor`, `SurfacePlacement` | `SurfaceLifecycle.kt` | Pure Kotlin. Turns `SurfaceHolder` callbacks into the ordered calls a renderer gets, counts surface generations, and computes margins from an anchor. |
| `NativeTerminalSurfacePlugin` | `NativeTerminalSurfacePlugin.kt` | Kotlin Tauri plugin behind three app commands. Runs on the UI thread against the Activity in front. |
| `native_terminal_surface_place`, `_remove`, `_state` (and `_look`, see [the look](#the-look)) | `apps/client/src-tauri/src/native_terminal_surface.rs` | Validates the renderer's arguments (session id, anchor, colour) and forwards them. Same shape as `edge_gesture_exclusion`: an app command with an ACL entry, the plugin itself unreachable from the page. `_remove` is allowed while the app is locked, like `terminal_core_close`; the others are not. |

The seam for the renderer is `SurfaceClient`: `onSurfaceReady(surface, generation, width, height)`, `onSurfaceChanged(...)` and `onSurfaceLost(generation)`. `TerminalSurfaces.clientFactory(id, background)` makes a session's client. The default is `NativeSurfaceClient`, the JNI renderer client below, with `BackgroundPainter` (fills the surface with the pane background) as its fallback, so a surface never shows undrawn memory.

## The renderer client

`NativeSurfaceClient` forwards each `SurfaceClient` call to `JniSurface` (`JniSurface.kt`, library `lazysh_lib`), whose entry points live in `native_terminal_surface/android.rs` and exist only in a build with the `native-terminal` feature. `ready` takes an `ANativeWindow` from the `Surface` and makes a wgpu surface on it (Vulkan, then GLES, per the renderer's policy: a CPU rasterizer is refused), draws the session of the same id from the core registry from a snapshot, and answers whether it can. `changed` resizes (and re-applies the pane colour and the display density), `lost` destroys the renderer's handles on the surface and releases the `ANativeWindow` before it returns, a newer generation draws the same session again from a snapshot (one host per session, kept across surfaces), and `remove` (the session's end) stops the host. A false answer, a missing library or a library built without the feature leaves the surface to `BackgroundPainter`; nothing crashes. The font is the system's `monospace` at 14 CSS pixels and the colours the default theme on the pane background until the page sends the user's preferences with the anchor. Calls run on the UI thread and `ready` waits for the GPU device to be created there.

Checked by `NativeSurfaceClientTest` (JVM: what the host is told and the fallback), `panes.rs` tests (host kept across generations, stale generation refused, removal) and `NativeTerminalSurfaceTest.theDefaultClientKeepsTheBackgroundForASessionTheRendererHostCannotDraw` (emulator). **Not established:** pixels of a core on the surface across stop/start and rotation (`PixelCopy` against the reference renderer) wait for the core running in the app on the emulator ([#2147](https://github.com/mihazs/lazysh/pull/2147)); the Android font directories, real GPU drivers and the UI-thread cost of device creation have not been measured.

### The GPU policy, and the debug switch for the CI emulator

The shipping policy refuses a CPU rasterizer (a device keeps xterm.js unless the native renderer beats it, which software cannot), and the CI emulator runs `-gpu swiftshader`. A **debug build on Android** therefore reads one more thing: when its process sets `LAZYSH_NATIVE_TERMINAL_SOFTWARE_GPU`, `native_renderer::policy()` allows a software adapter, for the probe (`native_terminal_probe`) and for `Target::on_window`. The instrumentation sets it with `Os.setenv` before it drives the page. The variable is not compiled into any other build: `.github/scripts/software-gpu-switch.sh` checks the built artifact, `present` on the debug libraries of `native-android-terminal-core` and `absent` on the release APK of `native-android-release-core`.

`native_terminal_probe` answers `available`, `reason`, `elapsedMs`, `adapter` (the adapter the renderer would run on: name, backend, device type, driver) and `seen` (every adapter its backends listed, chosen or not). The answer is kept per policy for the life of the process, so a case can ask under the shipping policy and under the switch. `NativeTerminalCoreTest.theProbeRefusesASoftwareRasterizerUnlessTheDebugSwitchAllowsOne` asks both, writes both answers with the device and the page's own wait to `/data/local/tmp/lazysh-evidence/native-probe.json` (`Evidence.kt`), and `tests/support/androidTerminalCore.ts` copies that file into the job's artifact (`lazysh-android-terminal-core-results`, `terminal-core-evidence/`) and prints it in the job log. The same case runs on the Waydroid lane ([runbook](waydroid-lane.md#the-native-probe-on-the-guest)).

## The look

The renderer draws with the preferences the page applies, not with a look of its own ([#2380](https://github.com/mihazs/lazysh/issues/2380)). `NativeTerminalAdapter.applyPreferences` sends `native_terminal_surface_look` (theme and palette with the selection colours, font family, font size in CSS pixels, which a pinch changes, bold as bright, the bold colour, and the default cursor style and blink) once for each change, one command at a time and in order, and again when the shell refused it. The shell keeps it per session (`panes::look`), so it may arrive before the surface exists and survives the surface being removed and placed again; the display's density and the pane's background still come from `place`, `ready` and `changed`. A surface that is drawing takes it at once (`Panes::relook`, `Host::set_look`), repainting every row from the renderer's copy of the screen. Before the page has sent one, a session is drawn with the system's monospace at 14 CSS pixels in the default theme. The command is refused while the app is locked, for a look the renderer cannot use (a font size outside 4 to 128, a family list that is empty, over 1,024 bytes or holds control characters, a colour that is not hex) and in a build with the kill switch.

Bold as bright and the bold colour are in the shared layout (`Appearance::bold`, `layout::row_draws`), so the reference renderer and the wgpu renderer colour a bold cell alike: a bold cell in palette colour 0 to 7 takes colour 8 to 15 of the theme, and one in the default colour takes the bold colour (before inverse and faint, as the xterm.js seam does). The cursor a program that chose none gets is the preference's style and blink: the core puts it in its frames (`TerminalRuntime::set_cursor_default`), and a program's own `DECSCUSR` 1 to 6 keeps its cursor until it gives it back with 0 or the terminal is reset (`ESC c`). The VT draws a steady block for both a program that sent nothing and one that asked for a steady block, so the runtime reads the cursor requests from the raw byte stream (`cursor.rs`, like the colour queries and the titles), not from the VT's state. **Limits:** only the 7-bit `ESC [ Ps SP q` is recognised, and one inside a string the VT skips (a DCS passthrough) is read all the same. `cursorAccent` and imported fonts ([#2223](https://github.com/mihazs/lazysh/issues/2223)) do not reach the renderer yet.

Checked by `panes.rs` (the look kept per session, refused when unusable, applied to a drawing session), `native_renderer::tests` on a software GPU (bold colours, the preferred cursor and a changed preference drawn with the reference renderer's pixels, the oracle for the cursor being a program that sets it), the `layout` and cursor cases in the runtime's `tests/renderer.rs` and the scanner's own tests, and `nativeTerminalAdapter.look.test.ts` (what is sent, when, and in order). **Not established:** pixels on an Android GPU; that waits for the first native session through the real UI.
### The first native session on the CI emulator

`NativeTerminalSessionTest` ([the case](../android-testing.md#a-native-terminal-session-through-the-real-ui-2390), job `native-android-terminal-session`) is the first run of a native session through the real UI on any Android environment. On the CI emulator (API 36 x86_64, SwiftShader Vulkan allowed by the debug switch) it chose Native in Settings, connected to an owned OpenSSH through the page, saw the core's prompt drawn by the renderer on the surface below the transparent WebView, typed a command through the surface's `InputConnection`, scrolled the pane back through 150 lines with a finger and got the same pixels back after a stop and start. The measurements it recorded (`native-session.json` in the job's artifact): the probe 313 ms cold (adapter `SwiftShader Device (Subzero)`, Vulkan, device type `Cpu`; the GL adapter `Android Emulator OpenGL ES Translator (Google SwiftShader)` was listed too), the session opened 8.4 s after the case started, the prompt drawn 1 s later, the typed command's answer drawn 2.5 s after that. Three defects were found on the way and fixed: the first probe crashed the app (`vkSetDebugUtilsObjectNameEXT` in the emulator's gfxstream driver, asked for by wgpu's debug build; [#2381](https://github.com/mihazs/lazysh/issues/2381)), and the surface kept its old pixels after a scroll because only output rang the renderer ([#2404](https://github.com/mihazs/lazysh/issues/2404)).

What it does not show: the grid is the 80 by 24 the core opens with, drawn in the top part of the pane (the pane's size does not reach the core yet), the look is the default theme, a software rasterizer is not a GPU, and nothing ran on Waydroid or arm64 from this case yet.

## Contract

- **One surface per placed session, below the WebView.** Anchor changes move or resize the same surface. Margins are measured from the content frame's padding box, where the activity's insets listener lays the WebView out, so system bars, cutouts and the keyboard move the surface exactly as they move the page; only the page's own layout needs a new `place`.
- **Generation.** `generation` starts at 0 and rises by one for every new surface the session gets (stop and start, hide, recreation). A resize keeps it. The client sees `ready` once per surface, any number of `changed`, and `lost` once, whatever order the window delivers its callbacks in. A zero-sized surface is no surface yet, and a late size after destruction does not bring a surface back.
- **Stop and start.** Android destroys a `SurfaceView`'s surface when its window stops and creates a new one on start. The session, its client and its generation count live in the registry, so the client is told `lost` and then `ready` with the new generation and draws the whole session again. A window that is only paused but still visible (multi-window) keeps its surface, and nothing is suspended: pausing is not a reason to stop drawing.
- **Activity recreation.** The registry outlives the Activity. When an Activity is destroyed its host views go (the client is told `lost`) and every session of that window is left unplaced, with its generation count kept. Nothing is shown on the new page until that page places the session again, so a stale pane never appears on a page that does not expect it. Whether a session may outlive its Activity at all is the open security decision in [runtime](terminal-runtime.md#lifecycle); this host decides nothing about it.
- **The WebView is transparent while a surface is placed, and only then.** The surfaces are below the WebView, and a WebView's own background is opaque white (wry sets no background colour), so a placed surface would sit behind a white page. `SeeThrough` (`TerminalSurfaces.kt`) calls `setBackgroundColor(TRANSPARENT)` on the WebView beside the host when a session is placed there and sets it opaque again when the last session placed beside it is removed or its Activity is destroyed. An xterm.js session never places a surface, so its WebView is never touched, and a page that paints its own background looks the same with or without a surface. Both are checked on the composited screen on the CI emulator and on [Waydroid](waydroid-lane.md#composition-cases-and-the-native-probe-on-the-guest-2383-2381), where each of the three cases passes on its own. A recreated Activity has a new, opaque WebView, which becomes transparent when its page places the session again. One frame of the opaque WebView background can show between the page marking a native pane (its ancestors then paint nothing) and the first `place` returning; it has not been measured.
- **Pixel format.** A `SurfaceView` asks for RGB_565 unless told otherwise, which quantises every colour (a pane background of `#1a2b3c` reads back as `#192d3a`). The host asks for `RGBA_8888` when it creates the view; a renderer that picks its own EGL or wgpu surface format must keep 8 bits per channel for the same reason.
- **Removal.** `remove` ends the surface and the session's count. Removing a session that is not there is not an error.
- **Gated by the choice, not by the build type.** `TerminalSurfaces.enabled` is true in every build ([#2306](https://github.com/mihazs/lazysh/issues/2306)); a release build no longer refuses on its own. The page asks for a surface only for a session whose backend the registry selected: never under Auto (`autoEligible` false), only when the user picked Native in Settings > Terminal engine (or a developer override), the probe passed and the build's kill switch (`LAZYSH_NATIVE_TERMINAL=off`, refused in Rust with `native_surface_disabled`-style errors) is not set. Otherwise the session stays on xterm.js. Not verified on a physical device.
- **Not owned here.** Touch, focus, IME and the soft keyboard (#1328), accessibility (#1329), and GPU device loss and thermal handling belong to the renderer and the later slices. The host view is not focusable and is hidden from accessibility until those exist.

## The page side

`apps/client/src/terminalSurfaceAnchor.ts` keeps a session's surface on a DOM element and is the only code that sends `place` and `remove` from the page. `TerminalPane` creates one for a session whose adapter is native (see [the pane](#the-pane)).

- **Hints, then a short look.** Layout, scroll, zoom and CSS transitions change an element's rectangle without telling the page which. A resize or scroll event, a `ResizeObserver` or `MutationObserver` callback, or a transition or animation event starts a frame-by-frame look at `getBoundingClientRect()` that ends after 12 frames with no change, so an idle page runs nothing.
- **One command in flight.** A rectangle that moved while a `place` was pending is not queued: when the command returns, the latest rectangle goes out as one command. The shell does not order commands, so `stop` waits for the command in flight before it sends `remove`, and a `remove` never overtakes a `place`.
- **No box, no surface.** An element that is hidden, zero-sized or detached ends the surface with `remove`; the next time it has a box it is placed again.
- **Refusal.** When the shell refuses or a command fails (a release build answers `native_surface_disabled`), tracking stops, a surface already placed is removed, and `onError` is told. The caller decides what to show; the tracker never retries.
- **Background.** The pane colour (`rgbOf` turns `#rgb`, `#rrggbb`, `rgb()` and `rgba()` into the `0xRRGGBB` the shell takes) is read on every placement, so a theme change reaches the surface with the next one.

Checked by `terminalSurfaceAnchor.test.ts` (Vitest, jsdom, frames driven by hand, the shell's commands mocked). Not established: the real placement round trip while a WebView scrolls or animates; it needs a device.

## The grid

The columns and rows of a native session are what its pane holds at the renderer's cell ([#2397](https://github.com/mihazs/lazysh/issues/2397)); before, `fit()` did nothing and the core stayed at its opening size, so a remote program drew for 80 x 24 whatever the pane was. The cell is the renderer's rule, `cell_metrics` in `native_renderer.rs` (0.6 x 1.2 of the font size, in whole device pixels, for a display density), and the page asks for it with `native_terminal_surface_cell(fontSize, dpr)`, once for each font size and density, so there is one copy of the rule. A surface is `round(css * dpr)` device pixels (`SurfacePlacement`), and the renderer draws whole cells from its top left, so the pane holds `floor(round(width * dpr) / cellWidth)` columns by `floor(round(height * dpr) / cellHeight)` rows (at most 1,000 each, the transport's bound): 49 x 43 on a 1080 x 1900 pixel pane of 14 px text at 2.625 pixels to a CSS pixel.

`NativeTerminalAdapter.fit()` (what `TerminalPane`'s `ResizeObserver` calls for a rotation, a soft keyboard or any layout change) requests that size when it differs from the grid; `requestSize` emits `resizeIntent`, the page's existing path sends it to the transport (`api.resize`) and the core follows the transport's resize, so the core, the remote PTY and the adapter's `size()` agree. A pinch or a font change asks for the new cell and fits again when it answers. `layoutRowHeight()` is one cell's height, `metrics()` reports the real cell and `cellAt()` uses it, so a pane that is not a whole number of cells has a margin at its right and bottom, not a stretched grid. A pane with no surface (no renderer), no box or less than one cell keeps its grid, and until the shell has answered nothing is fitted. Mosh's canonical resize is its own slice ([#1317](https://github.com/mihazs/lazysh/issues/1317)): `proposeSize()` now answers, and `enableCanonicalResize` is still absent.

Checked by `nativeTerminalAdapter.fit.test.ts` (Vitest over the stand-in core: the grid after each change of the pane, the font and the density, the touch-to-cell mapping, and that a refusal is asked again), `nativeTerminalAdapter.realCore.test.ts` (the same pane sizing the real core through its stdio harness, in `herdr-native`) and `native_renderer::tests::the_cell_a_page_divides_its_pane_by_is_the_cell_the_renderer_draws` (a drawn cursor block is the cell the command answers, at several sizes and densities). `native_renderer::tests::a_core_of_80_by_24_is_drawn_with_the_looks_a_phone_gets_before_its_page_sends_one_and_is_not_blank` draws an 80 x 24 core with the look a pane has before its page sends one (2.625 density, system fonts then the bundled font) and asserts light text pixels and a coloured cell, so a blank surface is not the renderer's layout, colours or default look on a host with a GPU (#2457). **Not established:** `stty size` through a live SSH session on an emulator, a rotation and `vim` filling the grid wait for the software-GPU switch and the first native session through the real UI; a font whose advance is not 0.6 em is drawn into the 0.6 em cell, so its text may look narrow or wide, but the grid still fits.

## The pane

`TerminalPane` mounts a session by the engine of its adapter (`adapter.backend`), and nothing else about the pane differs.

- **Native.** The terminal container gets an id (`useId`) and a `data-terminal-surface="native"` marker, the adapter is attached with `{kind: 'native', anchorId}`, and a tracker places the session's surface on the container for as long as the pane is shown (`active`, or `swiping` between the terminal and the Agent view). A pane that is hidden or ended stops the tracker, which sends `remove`; showing it again places the surface again. A refusal (a release build answers `native_surface_disabled`) is reported through the pane's `reportError`, the marker goes, and the page paints again.
- **Transparent over the surface, and only then.** While the marker is set, every ancestor of the container (`TerminalNativeSurface.css`: `:has(.terminal-canvas[data-terminal-surface="native"])`) paints no background, from the pane up to `html`. The pane's overlays (toolbar, composer, notices, search, selection tools) are not ancestors and keep their backgrounds above the surface. An xterm.js pane has no id and no marker, so no rule matches and its DOM is what it was.
- **Input stays on the container.** Pointer, touch, wheel and key handlers are still the container's and the pane's. A native adapter has no typed-input editor to observe (`observeInput` is absent without the `ime` capability), so the pane runs without the IME observer and offers no virtual modifiers; the platform's own input view is [#1328](https://github.com/mihazs/lazysh/issues/1328).
- **The surface colour** is the terminal theme's background, read on every placement.

Checked by `terminal-native-surface.spec.ts` (Playwright, Chromium, desktop and phone projects): the native adapter over the headless stand-in core in the app's own `app-viewport`, `app-shell`, `workspace` and `session-body` chain, with the shell's surface commands recorded. It asserts the placement rectangle and colour, that the surface follows a layout move, `remove` on hide and on unmount and `place` again on show, the computed background of every ancestor (transparent for native, opaque for xterm.js, opaque again when the pane is hidden or the shell refuses) and the alpha read back from a screenshot, the composer sheet painting and taking the hit above the container, and a finger drag on the container still scrolling. Not established: the real `App` chain (the harness repeats its class names, and the real page never mounts a native pane until a backend is registered), compositing on Waydroid or a device, and the cost of a translucent WebView. The Android WebView's own background is [the contract above](#contract), checked by `NativeTerminalCompositionTest`.
