# Windows, macOS and iOS native surface strategies

Status: **desk study, nothing run**. For [#1332](https://github.com/mihazs/lazysh/issues/1332) (Windows), [#1333](https://github.com/mihazs/lazysh/issues/1333) (macOS) and [#1330](https://github.com/mihazs/lazysh/issues/1330) (iOS), epic [#1302](https://github.com/mihazs/lazysh/issues/1302). The authoring host is Linux: there was no Windows, macOS or iOS machine, so no composition result for these platforms is asserted. What follows is read from the windowing stack the app ships (wry 0.57.1 and tao 0.37.2, from the root `Cargo.lock`), to say which composition strategy each platform can start from, what has to be measured, and what stays on xterm.js until it is. Related: [Linux PoC](linux-surface-composition-poc.md) (the one platform measured) · [Android PoC](android-surface-composition-poc.md) · [native rendering](native-rendering.md#composition-gate) · [platform integration](platform-integration.md).

All three platforms follow the composition rule the measured platforms arrived at: the native surface **below** a transparent web view, so DOM overlays (menus, the palette, the keyboard toolbar, selection handles) stay on top and gestures stay in the DOM. A platform where that cannot be arranged keeps xterm.js, because drawing the surface above the web view hides every overlay that intersects the pane (the Linux X11 result and the Android `SurfaceView` on top).

## What the shipped stack does

| Platform | Web view hosting in wry 0.57.1 | Transparency | Consequence for a surface below it |
| --- | --- | --- | --- |
| macOS | `WryWebViewParent`, an `NSView`, becomes the window's content view and the `WKWebView` is its only subview (`wkwebview/mod.rs`, around line 722) | `transparent` sets the private KVC key `drawsBackground` to NO on the configuration, and `set_background_color` repeats it on the instance (the source marks the instance call as private API) | A sibling `NSView` can be inserted into that content view below the web view (`addSubview:positioned:relativeTo:`); a layer-backed web view is expected to let it show through. The private key is a store-review question the app already carries for `transparent`. |
| iOS | The `WKWebView` is added to the window's `UIView` with `addSubview` (`wkwebview/mod.rs`, around line 767) | Always `setOpaque(false)`; the background colour is `systemBackgroundColor` unless one is given, so a transparent web view needs an explicit colour with alpha 0 | A sibling view (`MTKView` or a `CAMetalLayer`-backed `UIView`) can sit below the web view in the same parent; touches reach the front view, the web view, first. |
| Windows | **Windowed hosting**: `CreateCoreWebView2Controller` or `CreateCoreWebView2ControllerWithOptions` on the window's `HWND` (`webview2/mod.rs`, lines 429 and 431). The source has no composition-controller call. | `SetDefaultBackgroundColor`; wry forces any non-zero alpha to 255, so only alpha 0 is transparent. tao makes a transparent window with `DwmEnableBlurBehindWindow` and an empty region. | WebView2 paints into its own child window, so a sibling `HWND` is stacked against it by Z order. Whether a transparent WebView2 shows a *sibling* window behind it, and not just its parent's background, is the open question and is not answered by the source. Direct composition hosting (the web view as a visual under the app's own visual tree) would answer it, but wry does not offer it. |

## Strategy and decision per platform

| Platform | Strategy to prove | What the probe must assert (the Linux harness items) | Decision until it is proven |
| --- | --- | --- | --- |
| macOS | `CAMetalLayer`-backed `NSView` below the transparent `WKWebView` in `WryWebViewParent`; wgpu Metal surface from the `NSView` handle | Placement at a DOM anchor on a 1x and a 2x display, overlap (DOM box over the surface), resize, recreate, pointer and keyboard still reaching the web view, VoiceOver reading | xterm.js. A good candidate: the hierarchy is the simplest of the four. |
| iOS | `MTKView` or `CAMetalLayer` view below the web view in the window's `UIView`, from a Swift plugin shaped like `packages/apple-status` and a C ABI to the shared Rust renderer | The same, plus safe areas and the Dynamic Island, keyboard show and hide resizing once, and the lifecycle gates the iOS composition PoC ([#1311](https://github.com/mihazs/lazysh/issues/1311)) sets; `native-ios-simulator` hosts the XCUITest | xterm.js; [#1330](https://github.com/mihazs/lazysh/issues/1330) is conditional on #1311 and also depends on the core building for iOS ([#1312](https://github.com/mihazs/lazysh/issues/1312)). |
| Windows | First measure whether a child `HWND` **below** a transparent WebView2 shows through. If it does not, the options are a child window **above** with the overlay rectangles cut out of it (`SetWindowRgn`, fed by the page), or a wry that hosts WebView2 by composition (a fork or a patch; no change to wry is proposed here) | Placement under per-monitor DPI changes, overlap, resize, recreate, IME composition through TSF, device reset (`DXGI_ERROR_DEVICE_REMOVED`) and recovery from core state, Narrator and NVDA | xterm.js. The most likely platform to stay there: the straightforward arrangement is not known to work and the alternative changes the web view host. |

## How each can be covered without the hardware

- **Compile check.** The surface host code of each platform is written under `cfg(target_os = ...)` and must pass `cargo check` for `x86_64-pc-windows-msvc`, `aarch64-apple-darwin` and `aarch64-apple-ios-sim` on the Linux host where the targets and their crates allow it; CI already compiles all three (`native-desktop (windows-latest)`, `native-desktop (macos-latest)`, `native-ios-simulator`). A compile check says nothing about behaviour.
- **Probe runs in CI.** The plan is a probe like the Linux one that opens the real tao and wry window in the two desktop jobs and reads back its own window pixels (`PrintWindow` on Windows, a capture of its own window id on macOS). Whether the hosted runners' sessions allow it is unknown until the first run, the jobs are not required checks, and that first run is a measurement, not a gate. The iOS simulator job could do the same from an XCUITest.
- **Never inferred.** No platform's gate is recorded as passed from a compile, a source reading or a different platform's result, and a platform whose probe has not run keeps xterm.js.

## Open questions

- Windows: does a transparent windowed WebView2 show a sibling child window? Can the WebView2 background be made transparent at the same time as the host window is not layered (DWM blur-behind, as tao does)?
- macOS: is the `drawsBackground` private key acceptable for the App Store build, or is a public alternative needed (it is used today only when a window or web view is transparent)?
- iOS: does a `UIView` below a transparent `WKWebView` keep scrolling and hit testing of the web view unchanged ([native rendering](native-rendering.md#unresolved-questions))?
- All three: the same fractional-scale, input and accessibility gaps listed for [Linux](linux-surface-composition-poc.md#what-this-does-not-establish).
