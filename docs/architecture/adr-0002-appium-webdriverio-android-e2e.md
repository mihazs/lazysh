# ADR 0002: Appium and WebdriverIO regression suite for the Android app

- Status: **Accepted** for the structure, tooling and policy below. Each tool pin is verified by the scaffold issue before it merges (see [Validation](#validation-and-limits)). Date: 2026-11-12.
- Decision makers: repository maintainer. Tracking: [epic #1396](https://github.com/mihazs/lazysh/issues/1396), research issue [#1398](https://github.com/mihazs/lazysh/issues/1398).
- Related: [how-to](../how-to/write-and-run-appium-tests.md) · [conventions reference](../reference/mobile-e2e-conventions.md) · [regression index](../regression-tests.md) · [Android testing](../android-testing.md) · [Native GUI testing](../native-gui-testing.md).

## Context

Several regressions (Herdr scroll history shown as "Unavailable", keyboard resize and visibility, SwiftKey Backspace, gestures against Android navigation, toolbar pages, the Agent view composer) reached a real phone because no automated test drives the packaged Android app. The existing layers cannot:

| Layer today | What it cannot see |
| --- | --- |
| Vitest (`apps/client/src/**/*.test.*`) | Any real browser, WebView or device behaviour |
| Playwright (`apps/client/e2e`, 115 specs, Chromium with a phone viewport and a mocked bridge) | Android system gestures, a real IME, WebView insets, runtime permissions, the notification shade |
| Android instrumented tests (`gen/android/.../androidTest`, Kotlin) | Journeys across the WebView and Android; they are written in Kotlin and tied to one test runner |
| `apps/client/native-e2e` (WebdriverIO, `tauri-driver`, Vitest) | Android entirely: it drives the Linux desktop binary |

Facts established from the sources (all fetched 2026-11-12):

- Tauri documents WebDriver testing for desktop only. [tauri.app/develop/tests/webdriver](https://v2.tauri.app/develop/tests/webdriver/) says `tauri-driver` supports "only Windows and Linux" on desktop and never mentions Android or iOS. The [WebdriverIO Tauri service](https://webdriver.io/docs/desktop-testing/tauri/) is listed under "Desktop Testing" with Windows, macOS and Linux. Neither offers a mobile route, so Appium is the route on Android.
- Appium's UiAutomator2 driver controls the native layer and, through ChromeDriver, a debuggable Chrome-based WebView as a second context ([Hybrid Applications](https://appium.github.io/appium-uiautomator2-driver/latest/guides/hybrid/)). A Tauri Android app is exactly that shape. The current Waydroid guest has a live `webview_devtools_remote` socket for the debug build and WebView 153.0.8010.36; Chrome for Testing downloads are reachable.
- WebdriverIO 10 requires Appium 3 for `@wdio/appium-service`; the service refuses Appium 1 and 2 ([service docs](https://webdriver.io/docs/appium-service)). UiAutomator2 driver 9.x peers on Appium 4 beta; driver 8.7.3 peers on Appium `^3.0.0-rc.2`. Appium 3.9.0 is the current stable.
- A spike (private prefix under `/tmp`, nothing installed on the repository or any device) installed Appium 3.9.0 and driver 8.7.3 with `appium driver install` (both `--source=local` and `--source=npm`), started a server with `--allow-insecure=uiautomator2:chromedriver_autodownload` and got `{"ready":true}` from `/status`. WebdriverIO CLI 10.1.0 (the version this repository already pins) has `--shard x/y`.

## Decision

1. **Stack.** WebdriverIO 10 test runner with the **Mocha** framework, TypeScript, the `@wdio/appium-service` to start Appium 3.9.0, and the UiAutomator2 driver 8.7.3. Assertions are the built-in auto-retrying `expect-webdriverio` matchers. All `@wdio/*` packages and `webdriverio` use one exact version (10.1.0 today, matching `apps/client`); they are bumped together. Node 24 from `.prototools` satisfies Appium 3 (`^20.19 || ^22.12 || >=24`). Mocha, not the Vitest adapter: the WebdriverIO docs keep Mocha as the default, the Vitest adapter skips several suite hooks and does not forward WebDriver commands to reporters, and one Android device gives no concurrency to gain. The desktop suite stays on Vitest and `tauri-driver`; this decision does not touch it.
2. **Location.** A new directory **`apps/client/mobile-e2e/`**, a sibling of `e2e` (Playwright) and `native-e2e` (desktop WebdriverIO), with its own `tsconfig.json`. It is not a new workspace package: dependencies go in `apps/client/package.json` (as `webdriverio` does), tasks in `apps/client/moon.yml` beside `build-android-emulator`. The layout follows the WebdriverIO page-object guide (`pageobjects/`, `specs/`) and Tauri's own example (a `wdio.conf` plus `specs/*.e2e.*`). Spec files end in `.e2e.ts` so no Vitest glob picks them up. Tests are not mixed into `native-e2e`: that tree has a different runner, driver, platform and isolation model (see [layout](../reference/mobile-e2e-conventions.md#directory-layout)).
3. **Two contexts, one explicit switch.** Sessions start in `NATIVE_APP`. A support helper switches to the app WebView by title or URL match with a raised connection retry time for slow starts (`switchContext` accepts both, [docs](https://webdriver.io/docs/api/mobile/switchContext)) and back. Specs and page objects declare which context an element lives in; tests never call `switchContext` themselves. ChromeDriver comes from `chromedriver_autodownload`, scoped `uiautomator2:` as Appium 3 requires, with a cached `appium:chromedriverExecutableDir`.
4. **Page Object Model, components not screens.** One object per significant component (side menu, toolbar, terminal surface, Agent composer, host form), per [Fowler](https://martinfowler.com/bliki/PageObject.html): getters return lazy elements, methods are user-level actions, **no assertions in page objects**, exported as singletons as the [WebdriverIO guide](https://webdriver.io/docs/pageobjects) shows.
5. **Selectors.** Native context: `~accessibility id` (content-desc), then `id=` resource id, then `UiSelector`; never XPath. WebView context: accessible name first (WebdriverIO's `aria/<name>` strategy, falling back to `[aria-label="..."]` if the scaffold finds it does not resolve through ChromeDriver on Android; this mirrors the roughly 2,100 `getByRole` calls in the Playwright suite), then `[data-testid]`, never classes or structure. The UI is localized, so every run pins the device to `en-US` and text selectors are the last resort. A test id is added only where no unique accessible name exists, kebab-case `area-element` (`toolbar-page-dots`); only `side-menu` and `side-menu-<id>` exist in the app today (`surface` lives in a unit test), next to the older `data-toolbar-page` and `data-workspace-mode` attributes, so each test issue adds the ids it needs. Rationale: the [WebdriverIO selector guide](https://webdriver.io/docs/selectors), the [Testing Library priority](https://testing-library.com/docs/queries/about/#priority) and [Playwright best practices](https://playwright.dev/docs/best-practices) agree that user-perceivable queries come first and test ids are a stable contract for what remains.
6. **No sleeps.** WebdriverIO's [best practices](https://webdriver.io/docs/bestpractices) ("Don't pause") and [Fowler on non-determinism](https://martinfowler.com/articles/nonDeterminism.html) agree. Waiting is the auto-retrying matchers or `waitUntil` with a `timeoutMsg`. The suite enforces it by behaviour, not by text search: the `before` hook overwrites `browser.pause` so a call throws. A missing `await` is the other classic WebdriverIO flake, so `mobile-e2e` alone gets strict `tsc --noEmit` plus a scoped ESLint run (`@typescript-eslint/no-floating-promises` and `eslint-plugin-wdio`, both recommended by [WebdriverIO](https://webdriver.io/docs/bestpractices) and [Playwright](https://playwright.dev/docs/best-practices)); the repository has no ESLint today, and this scope does not change that for other code.
7. **Isolation and reset.** One Appium session per spec file with `appium:noReset: false` (app data cleared at session start, no uninstall); each test creates uniquely named hosts from a per-run nonce and removes them; tests never depend on order. Device state (window size, density, navigation mode, IME, animation scale, rotation, permissions) is only changed through one support module that records the baseline and restores it in `after`, under an advisory lock per device serial, because the local Waydroid guest is shared with other agents. The suite never uses Appium's `adb_shell` insecure feature; `adb` runs from the Node support layer against `ANDROID_SERIAL`.
8. **Fixtures reuse the existing owned hosts.** `tests/support/sshFixture.ts` (`SshFixture`), `androidHerdr.ts` (`HerdrFixture`) and `androidTmux.ts` (`TmuxFixture`) already start private loopback OpenSSH, Herdr and tmux with generated keys. `SshFixture` is already shared with the desktop suite, so it runs under Node; the fixtures issue confirms the same for the Herdr and tmux fixtures. The suite starts them once per run in `onPrepare`, writes endpoint and key to a mode-0600 file under the run directory, and routes the guest to the host with the same `adb reverse` the instrumented tests use. Nothing is duplicated.
9. **Tags and tiers.** The directory is the tier: `specs/smoke`, `specs/regression`, `specs/journeys`, each a named WebdriverIO suite. Title tags are only cross-cutting: `@flaky` (quarantined), `@emulator-only` (cannot run on Waydroid), `@slow`.
10. **Retries and quarantine.** Locally nothing retries. CI uses `specFileRetries: 1` (a fresh session, because device state is the dominant flake source) and Mocha `retries: 0`; a spec that passes only on retry is reported as flaky. A flaky test is tagged `@flaky`, links an issue, moves to the non-gating quarantine run, and is capped at five tests and 14 days, following [Fowler's quarantine guidance](https://martinfowler.com/articles/nonDeterminism.html) and Google's [flaky-test data](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html) (about 1.5 percent of runs flaky; re-run to detect, quarantine when too flaky).
11. **Reporters and artifacts.** `spec` for the console and `junit` for CI; Allure is not adopted now (it needs a Java renderer and adds nothing the JUnit report plus artifacts do not give). On failure: screenshots of both contexts, native and WebView page source, a bounded `logcat` tail and the Appium log. Screenshots are suppressed while a private key or password is on screen, the rule the desktop suite already follows.
12. **CI.** A path-filtered job runs the suite on the same API 36 x86_64 emulator runner as `native-android-runtime`, builds or downloads the x86_64 debug APK, publishes JUnit and failure artifacts, and uses `wdio run --shard x/y` in a matrix only when wall time exceeds 25 minutes (one emulator serves one session, so shards are separate jobs). It starts report-only and becomes a required check after 20 consecutive green runs on `main`; changing required checks remains a maintainer action.
13. **Test pyramid placement.** The lowest layer that can fail on the defect owns the test ([Android strategy](https://developer.android.com/training/testing/fundamentals/strategies), [Fowler's Test Pyramid](https://martinfowler.com/bliki/TestPyramid.html), [Google, "Just Say No to More End-to-End Tests"](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html)). Google's guidance is roughly 70 percent unit, 20 percent integration and 10 percent end-to-end, "broad and shallow" at the top. Appium tests are the tip: at most ten smoke journeys plus one regression test per bug that only exists on a device. The placement table is in the [reference](../reference/mobile-e2e-conventions.md#where-a-test-belongs).
14. **Regression policy.** Every bug fix lands a regression test that fails on the parent commit, at the lowest layer that reproduces it, and a row in [`docs/regression-tests.md`](../regression-tests.md). A defect only observable on a device also gets an Appium test; it may follow in a linked PR, and the bug issue stays open until the index row is active. The rule enters `AGENTS.md` and the PR template through the process issue.

## Alternatives considered

| Alternative | Why not chosen |
| --- | --- |
| Extend `native-e2e` | Different runner (Vitest with standalone `remote()`), driver (`tauri-driver`), platform and namespace isolation; mixing them couples desktop CI to Android and breaks the `include: native-e2e/**/*.spec.ts` config |
| `@wdio/tauri-service` on Android | Documented for Windows, macOS and Linux only; no mobile provider |
| WebdriverIO Vitest adapter | Fewer hooks, WebDriver commands not forwarded to reporters; concurrency gives nothing with one device |
| Cucumber | Real tags and retry filters, but adds a Gherkin layer nobody asked for; Mocha titles plus page objects read as intent already |
| Maestro, Detox | Not the requested stack; no WebView-context access of the same fidelity |
| Appium with the `adb_shell` feature for gestures and navigation mode | Widens the insecure surface of the Appium server; `adb` from Node under a device lock is narrower and testable |
| Allure now | Java renderer and extra CI step for no new information over JUnit plus artifacts |
| Only more Playwright and instrumented tests | They cannot reproduce system gestures, IME or WebView insets together on a real Android runtime |

## Consequences

Positive: bugs found on a phone become repeatable tests; one place documents the conventions; fixtures are shared with the Android instrumented and desktop suites; the Waydroid guest is protected by a lock and restore step.

Negative or risky:

- The suite is the slowest layer. The placement rule and the ten-test smoke cap exist to keep the pyramid from inverting.
- Appium 3 plus UiAutomator2 8.x is one major behind the driver's newest line; moving to Appium 4 and driver 9 is a planned, separate upgrade once Appium 4 is stable and `@wdio/appium-service` supports it.
- WebView tests depend on the debug build exposing the WebView (it does today) and on ChromeDriver matching the guest WebView; the cached mapping and `chromedriver_autodownload` need outbound access to Google storage.
- Waydroid is Android 13, x86_64, 3-button navigation by default and not One UI. It stands in for the emulator locally; real-device and Samsung checks stay with the user.

## Validation and limits

- Verified in this research: package versions and peer ranges from the npm registry, Appium 3.9.0 plus driver 8.7.3 install and `/status` readiness, the `--allow-insecure=uiautomator2:` flag syntax, `--shard` in the `@wdio/cli` 10.1.0 source, and the presence of a WebView debugging socket and WebView version on the Waydroid guest (read-only `adb`).
- **Not verified in the research**: an Appium session on the Waydroid guest or the CI emulator, ChromeDriver attach to the Tauri WebView, `noReset: false` clearing app data on this app, WebdriverIO's `aria/` strategy through ChromeDriver, and `adb reverse` over the network ADB transport. Starting UiAutomator2 installs two helper packages and takes the device's single UiAutomation slot, which would disturb the other agent using the shared guest.
- **Verified by the scaffold (2026-11-12, Waydroid Android 13 x86_64, network ADB)**: Appium 3.9.0 with driver 8.7.3 created a session; ChromeDriver 153.0.8010.52 was downloaded by `chromedriver_autodownload` for the guest WebView 153.0.8010.36 and attached to the Tauri WebView (title `lazysh`); `noReset: false` cleared the app data (the home showed "Add your first host" although hosts existed before); `aria/<name>` resolves through ChromeDriver (WebdriverIO turns it into an XPath on `aria-labelledby` and content); the WebView DevTools socket appears a moment after the activity starts and `switchContext` does not wait for it, so `support/contexts.ts` waits first. `adb reverse` over network ADB is still open and belongs to the fixtures issue. A failing test restored the guest window size to its baseline, and `browser.pause` threw inside a session.
- Several fetched pages were incomplete (the Google flaky-test post and the descriptive-names post returned only comments); those claims are cited from search summaries and marked as such in the reference.
