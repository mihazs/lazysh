# Remote decisions for a waiting Claude hook

lazysh supports opt-in decisions for the `PermissionRequest` hooks of Claude Code and [Codex](#codex), and for the `permissionRequest` hook of [Copilot CLI](#copilot-cli). Each decision returns to the originating waiting hook's stdout. It never types into a terminal, chooses a pane by its current title, starts another agent, or changes permission rules.

Print the configuration fragment:

```sh
lazysh-agent approval-config
```

Merge the printed `PermissionRequest` entry with your existing Claude settings yourself. Keep the ordinary lifecycle hooks from `lazysh-agent claude-config` as well. No command edits settings automatically. The fragment gives the hook a 300-second decision deadline and a slightly longer Claude timeout.

The protocol follows the [official Claude hooks reference](https://code.claude.com/docs/en/hooks#permissionrequest). This event runs when a tool needs permission. Its response uses `hookSpecificOutput.decision.behavior` with `allow` or `deny`. A deny may carry a `message` that Claude reads (at most 500 characters, one line). An allow may carry exactly one of the request's own `permission_suggestions` as `updatedPermissions`; lazysh never sets updated inputs, never builds a rule of its own, and never edits a settings file (Claude Code applies the update where its `destination` says). Other configured policies still apply. PreToolUse, sandbox-network prompts, interactive questions and agent CLIs other than Claude Code, Codex and Copilot CLI are not claimed as supported approval paths.

An immutable request binds a random UUID, SHA-256 content hash, Claude session, project, the pane the hook runs in when it can be named exactly, exact tool name/input, creation time and expiration. The pane is the hook's own multiplexer identity, taken from its environment and never from the pane that is active or focused when a decision arrives: tmux's `TMUX_PANE` as `%7`, else Zellij's session and terminal pane as `zellij:<session>:<pane>` (from `ZELLIJ_SESSION_NAME` and `ZELLIJ_PANE_ID`), else a Herdr pane as `herdr:<session>:<pane id>` such as `herdr:default:w3V:p1`. A Herdr pane is named only when `HERDR_ENV` is `1`, `HERDR_PANE_ID` is a public pane id and `herdr session list --json` shows exactly one running session whose API socket is `HERDR_SOCKET_PATH`; a stopped, unknown, ambiguous or unreadable session, a missing `herdr` or a custom socket names no pane. tmux wins over Zellij and Herdr, and Zellij over Herdr, so a pane that inherited another multiplexer's variables is named by the first of them (a Herdr server started inside tmux hands its panes the outer `TMUX_PANE`). A malformed `TMUX_PANE` refuses the hook, and a request without a pane is listed with a null `paneId` and can only be answered without a pane id: no pane id, however well formed, answers it. The decision carries the listed pane unchanged, so a pane replaced by another pane or session, or by another multiplexer, is refused; the hook's own lease still ends the request when its process ends, so a closed pane cannot be answered. The agent board's row for a Herdr hook names no pane, as before. Plain terminal hooks can also use the direct response path: the originating hook process supplies the identity, so a multiplexer is not required. The UI must display the complete tool input before an explicit decision.

The hook holds an exclusive OS file lock on its private request lease. Listing hides expired requests and removes requests whose originating process has exited. Resolution requires the exact UUID, hash, session and pane and atomically updates a still-pending, unexpired row. Concurrent decisions have one winner. A cancelled hook releases its lease, and its token cannot target another hook even if session, pane and tool input repeat. Timeout returns a denial. A decision accepted immediately before process cancellation may never reach Claude; acceptance is not proof of tool execution.

With the opt-in [nested-agent switch](reference/companion-settings.md#notification-policy-nested-agents-and-an-unlocked-desktop) on, a request from a Claude Code or Codex session that another agent started takes no approval: nothing is listed for the phone, the hook prints no decision and the agent decides as it would without the hook (Codex shows its own terminal prompt). The summary below is still recorded.

The companion emits a bounded `PermissionRequest` summary to the normal event store for the agent board and notifications. It does not infer that a tool started from an approval: normal subsequent lifecycle events establish working/done state.

The separate private state directory `approvals/` contains the approval SQLite database and lease files. Unlike lifecycle summaries, pending approvals intentionally contain exact tool arguments, which can include sensitive data. Directory/database permissions are restricted on Unix; SQLite secure-delete is enabled and consumed, expired or cancelled rows are removed. This is not a promise of forensic erasure from storage or filesystem snapshots. The local user's account remains the trust boundary.

Bounds are 32 simultaneous hooks, 16 KiB of encoded tool arguments per request, 20 requests per list, and 1–600 seconds per hook. Oversized or malformed hooks fail with sanitized diagnostics and no decision output; inspect Claude's normal permission surface. Each list entry contains enough identity to resolve. When Claude suggested permission updates, the entry also lists them as `options`, rebuilt field by field from the payload and covered by the request hash: allow rules (`addRules` with `behavior` allow), a mode other than `bypassPermissions` (`setMode`) and added directories (`addDirectories`), at most 8 each bounded in size. Deny and ask rules, removals, unknown types, unknown destinations and `bypassPermissions` are dropped, so they are never offered. An older companion omits `options` (an empty list is always listed), so the client offers it no message form:

```sh
lazysh-agent approval-list --limit 20
lazysh-agent approval-resolve --id REQUEST_UUID --expected-hash HASH --session-id SESSION_ID --pane-id '%7' --decision deny
```

Pass the listed `paneId` unchanged (`%7`, `zellij:work:3` or `herdr:default:w3V:p1`), and omit `--pane-id` only when the listed pane is null. `--option N` (an index into the listed `options`, allow only) allows with that suggestion; `--message TEXT` (deny only) denies with a message. An out-of-range index, an option with a deny, a message with an allow and a message that is blank, longer than 500 characters or has a control character are refused with no output and leave the request pending. A stale or mismatched resolution exits unsuccessfully with no success JSON. Integration tests use fixture hook subprocesses to verify exact identity (including the Zellij and Herdr panes, which they simulate with the environment those multiplexers export and a stand-in `herdr session list`), concurrent resolution, cancellation, timeout, replay refusal and payload removal. No real Claude session was used to certify host-version behavior.

## Codex

Codex has the same `PermissionRequest` hook, and a Codex prompt is answered the same way: through the hook's own decision, never by typing into the pane.

```sh
lazysh-agent approval-config --agent codex
```

Merge the printed entry into Codex's `hooks.json` yourself (keep the lifecycle hooks from `lazysh-agent codex-config` too) and review it in Codex's own hook trust prompt; lazysh never accepts hook trust. The decision follows the [Codex hooks reference](https://learn.chatgpt.com/docs/hooks): `hookSpecificOutput.decision.behavior` is `allow` or `deny`, and a deny may carry a message Codex shows. Codex fails closed on `updatedInput` and `updatedPermissions`, so lazysh never sends them. The request is the same immutable record as Claude Code's (random UUID, hash over agent, session, project, pane, tool name and input, expiry), listed by `approval-list` with `"agent":"codex"` and answered by `approval-resolve` with the same identity, so one agent's hash never answers another agent's request.

Codex differs from Claude Code in two ways that change what a person at the terminal sees:

- Codex draws its own approval prompt only after the hook returns. While a request is pending the terminal shows "Running hook" and no prompt, so the terminal cannot answer it first. **Esc** in the terminal interrupts the turn, which ends the hook and removes the request; nothing runs.
- A request nobody answers before its deadline gives **no decision**, and Codex then shows its normal prompt in the terminal. The fragment waits 120 seconds (`--timeout-seconds` changes it; keep Codex's own `timeout` longer). Claude Code's expired requests are denied, but a denial here would hide a prompt the person at the keyboard can still answer. A hook that fails, or whose tool input is not a JSON object or is larger than 16 KiB, likewise leaves Codex to ask in the terminal.

Checked with the real Codex CLI 0.167.0 driving the real `lazysh-agent` hook against a local stand-in model server in a private tmux: the pasted fragment loads after trust, the request carries Codex's session id and tmux pane, an allow runs the command, a deny with a message shows "Blocked by hook" with that message and runs nothing, a wrong pane is refused, Esc removes the request, and an expired request shows Codex's own prompt. That run is manual: CI has no Codex CLI, so CI runs the hook subprocess tests only. Codex's other approval requests (MCP tools, `apply_patch`, network access) and a Codex on another host or in Herdr or Zellij were not exercised. The Agent view dock on tmux lists a Codex request too, for the pane and session its report names, and answers it the same way as the Agents board; that dock is covered by a mocked Agent view test against the companion's request format, not yet by a run against a real Codex.

## Copilot CLI

Copilot CLI's `permissionRequest` hook can carry a decision, and a Copilot request is answered the same way: through the hook's own output, never by typing into the pane.

```sh
lazysh-agent approval-config --agent copilot
```

Save the printed version-1 hook file in Copilot's hooks directory yourself (keep the lifecycle hooks from `lazysh-agent copilot-config` too) and review it in Copilot's `/hooks` under its normal policy; nothing installs it for you. It runs `lazysh-agent` shell-free (`exec` and fixed `args`) and waits 120 seconds (`--timeout-seconds` changes it; keep `timeoutSec` longer, because Copilot's own default is 30). The decision follows the [Copilot hooks reference](https://docs.github.com/en/copilot/reference/hooks-reference): `behavior` is `allow` or `deny` at the top level of the output (not nested like Claude Code's and Codex's), and a deny may carry a `message` the model reads. lazysh never sets `interrupt`, which would stop the whole agent, and Copilot takes no permission updates, so a Copilot card offers Allow, Deny and **Deny with a message**. The request is the same immutable record as the others (random UUID, hash over agent, session, project, pane, tool name and input, expiry), listed with `"agent":"copilot"` and answered with the same `approval-resolve`, so one agent's hash never answers another agent's request. Copilot names its fields in camelCase (`sessionId`, `toolName`, `toolInput`, `hookName`); a payload in any other spelling, of another event, with a tool input that is not an object or is over 16 KiB, makes the hook fail with no decision and no stored request. It never exits with code 2, which Copilot reads as a denial.

Copilot's hook differs from Claude Code's and Codex's in three ways that matter before you turn it on:

- **It runs before Copilot's own rules, not only when Copilot would ask.** Every shell command, file edit and other tool call that needs a permission check becomes a request that you answer or let expire, including the ones Copilot would run without asking (a plain `echo`, and everything under `--allow-all-tools`). While it waits, the terminal shows "Working" and no prompt. Use it for a session you are away from, and narrow it with Copilot's `matcher` (a regular expression over the tool name, for example `"matcher":"^(bash|edit)$"`) if you only want some tools.
- **An Allow skips Copilot's rules, and a Deny ends the request.** With `--deny-tool='shell(touch)'` Copilot blocked `touch`; with this hook installed the same command ran after an Allow from lazysh. Do not rely on a `--deny-tool` or other deny rule as a limit on what a tap on your phone can run. The card shows the complete tool input before you decide.
- **Nobody answering means no decision, not a denial.** A request that expires gives no output, and Copilot then applies its own rules and shows its normal prompt in the terminal (a denial would hide a prompt the person at the keyboard can still answer). Pressing **Esc** twice in the terminal interrupts the turn, which ends the hook and removes the request. A hook that fails likewise leaves Copilot to ask.

Checked with the real Copilot CLI 1.0.105 on Linux driving the real `lazysh-agent` hook, in a private home against a local stand-in model server (Copilot's own bring-your-own-model settings, offline) and a private tmux: the printed fragment loads, the request carries Copilot's session id and tmux pane and shows on the board as needing attention, an Allow runs the command, a deny with a message reaches the model as "Permission denied by a PermissionRequest hook: ..." and runs nothing, a wrong pane, a wrong hash and a second answer are refused, an unanswered request shows Copilot's own prompt after its deadline, two quick Esc presses remove the request, a file edit arrives as an `edit` request with its diff, and a `matcher` of `^edit$` leaves shell commands out. That run is manual: CI has no Copilot CLI, so CI runs the hook subprocess tests only. MCP tools, URL requests, Copilot's sandbox-bypass requests (the reference says an Allow does not pre-approve those), sub-agents, a Copilot on another host or in Herdr or Zellij, macOS and Windows were not exercised. The Agent view dock still lists Claude Code's requests only; a Copilot request is answered from the Agents board.

## Choosing an option

The approval card and the Agent view dock show Allow and Deny, then each suggested update as its own button and **Deny with a message**. A suggestion is never a default and never one tap: it opens a confirmation that names where Claude Code will keep it (this session only, the project's local settings, the shared project settings or the user settings) and shows the exact rule, mode or folders; **Cancel** sends nothing. The message of a denial is a single line the agent reads as the reason. A Codex or Copilot request lists no suggestions (neither takes any), so its card offers Allow, Deny and **Deny with a message**. The other agents have no approval hook here, so their prompts stay in the terminal. A list dialog of Claude Code or Codex that has no hook decision (a model or trust list, Codex's question) is answered by the Agent view's dialog card with arrows and Enter, and only after the host captures the pane again and finds that dialog once ([List dialogs](agent-view.md#list-dialogs)); an agent without such a profile has no way to be answered remotely.

## In the Agent view

On a native tmux session, the Agent view shows the pending requests of the Claude Code session whose hook report names its pane (and no other) above the conversation. A decision is the same hash-bound `resolve_agent_approval` call as on the Agents board, sent only after the pane and the single reported session are checked again, and the buttons ignore taps for 400 ms after a card appears. Nothing is typed into the terminal, so switching to the terminal shows the prompt already answered through the hook. Before it sends, the view lists the host's pending requests once more: a request answered in the terminal first (or on another device) is no longer listed, so nothing is sent and the view says it was already answered. A conversation chosen from the session list, and any pane without exactly one matching report, shows no requests there; the Agents board still lists them.

Under Zellij the dock shows the requests whose pane is exactly the `zellij:<session>:<pane>` of the one report that names a pane of the attached session (the pane the composer sends to). Zellij has no read of the pane a terminal shows, so the report is the evidence: several reports naming panes of the session, a report with no pane, or a request of another pane, session or multiplexer show no request there. Before it sends, the view reads the reports again and sends only while they still name exactly that pane, agent session and Zellij session.

Under Herdr the same dock shows for the agent of the focused pane. It matches the requests of the one session id Herdr reports for that pane that name exactly `herdr:<attached session>:<focused pane id>`, or no pane (a request from a companion older than the exact-pane approvals); one that names another pane or server is never shown. The decision is the same hash-bound `resolve_agent_approval` call with the request's own pane. Before it sends, the view reads Herdr's tree again and sends only while exactly one live agent names this session in this pane and terminal and Herdr reports that pane as the focused one, and lists the host's pending requests once more. An agent picked by hand from the list is read-only here, as it is for input.

## Agents that keep their prompt in the terminal

An agent whose hook cannot express an Allow keeps its prompt in the terminal, and lazysh does not offer a decision for it. Cursor CLI, Droid, Gemini CLI, Amp and Cline have not been checked against an installed CLI yet, so none of them is claimed either way ([#1797](https://github.com/mihazs/lazysh/issues/1797)).

### Kimi Code

Kimi Code 2.4.1 has no hook that can carry an Allow, so a Kimi prompt is answered at the terminal. `lazysh-agent kimi-config --dialect kimi-code-2.4` (see [the agent hooks guide](agent-hooks.md#gemini-cli-droid-and-kimi-cli)) still shows "Approval requested" on the Agents board; that is a notification and has no buttons.

- `PermissionRequest` and `PermissionResult` are fire-and-forget observers: Kimi starts the hook, never reads what it prints and never waits for it ([source of 2.4.1](https://github.com/MoonshotAI/kimi-code/blob/2c73f3f50af4fa7f2540ca0d2e33b07a1408e3a7/packages/agent-core-v2/src/features/externalHooks/agent/agentExternalHooksService.ts#L178)).
- `PreToolUse` is the only tool hook whose answer is read, and only to **block**: exit code 2, or `hookSpecificOutput.permissionDecision` of `deny` ([`runHook.ts`](https://github.com/MoonshotAI/kimi-code/blob/2c73f3f50af4fa7f2540ca0d2e33b07a1408e3a7/packages/agent-core-v2/src/features/externalHooks/internal/runHook.ts#L140)). There is no allow. It also runs for every tool call, before any approval is requested, so a hook that blocked would deny each call without ever showing a prompt; that is a policy, not an Allow and Deny pair for the prompt the person is looking at.

Checked with the official 2.4.1 Linux x64 release (SHA-256 `f4a225fb...d738de`), in a network-less sandbox against a synthetic endpoint, in Kimi's manual permission mode ([the qualification harness](reference/kimi-code-qualification/README.md), scenarios `allow_printed` and `pretooluse_exit_2`): hooks on `PermissionRequest` and `PreToolUse` that printed an allow in each spelling the supported agents use (Claude Code's and Codex's nested `hookSpecificOutput.decision.behavior`, Copilot's top-level `behavior`, Kimi's own `permissionDecision`, and `decision: "approve"`) ran, and the prompt still waited: four seconds later no `PermissionResult` and no tool event had arrived, and the tool ran or failed only when the person answered. A `PreToolUse` hook that exited 2 stopped the tool with no prompt and no `PermissionRequest`.

Not covered: release 2.6.2 (the harness does not run on it, see its README), a real provider or account, macOS and Windows. A later Kimi release that reads a decision from these hooks would need this check again before lazysh offered one.
