# 90-day maintainer execution calendar

Planning window: **2 November 2026 – 30 January 2027** (90 calendar days).
These are future maintainer activities, not announcements or contacts already
performed. The release acceptance gates control launch timing; postpone outward
launches if installation or native behavior is not trustworthy.

| Week | Dates | Maintainer action | Evidence / exit condition |
| --- | --- | --- | --- |
| 1 | Nov 2–8 | Resolve release hold with existing owners; review README/Obtainium and community PRs; configure private reporting | Applicable CI reviewed, publication separately verified, support paths checked |
| 2 | Nov 9–15 | Invite a small opt-in set of developers through existing contacts, with maintainer authorization | Voluntary exact-version install/SSH feedback, no host/session collection |
| 3 | Nov 16–22 | Triage first-use friction; collect real native screenshots and reconnect recording | Reviewed privacy receipt and passing native steps, failures tracked |
| 4 | Nov 23–29 | Publish reviewed tmux tutorial only after its native walkthrough is executed | Version/device/prerequisites recorded; no persistence overclaim |
| 5 | Nov 30–Dec 6 | Review starter issue difficulty and help first contributors choose one | Bounded ownership, executable checks, unanswered questions triaged |
| 6 | Dec 7–13 | Prepare agent-workflow tutorial against one supported integration | Real host/companion version and tested limits, draft reviewed |
| 7 | Dec 14–20 | Rehearse installation from a fresh profile; check landing/download links on phone and desktop | Measured steps/time reported by consenting testers, no invented activation rate |
| 8 | Dec 21–27 | Assess Show HN readiness; allow for maintainer holiday availability | Stable preview path, real demo, disclosure policy and time to answer questions |
| 9 | Dec 28–Jan 3 | Submit only if maintainer approves and can support responses; otherwise defer | Record actual URL/date; no coordinated votes or stars |
| 10 | Jan 4–10 | Choose one relevant Reddit/developer community, read current rules and disclose authorship | Permission/rules verified; technical question and limitations included |
| 11 | Jan 11–17 | Review appropriate OSS directories and their submission criteria | Manual maintainer-approved submissions only; no claimed listing before acceptance |
| 12 | Jan 18–24 | Credit actual merged contributors; ask about onboarding friction without pressuring repeat work | Linked PR credits, optional feedback and a feasible follow-up task |
| 13 | Jan 25–30 | Review 90-day evidence, unresolved installation failures and contributor return patterns | Published aggregate scorecard and next priorities with uncertainty stated |

Every Monday the triager updates the [scorecard](scorecard.md), checks unanswered
external issues and PRs, and chooses one small correction. Every release maintainer
refreshes support, asset and signing statements. Every public post gets a fresh
review of platform maturity and current community rules. No outreach is executed
by this calendar, and no growth outcome is promised.
