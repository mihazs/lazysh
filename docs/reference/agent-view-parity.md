# Agent view parity: screen elements, reference apps and gaps

Status: reference, audited 2026-11-11 against `main` at `7f16dcee`; the element rows were refreshed on 2026-11-14 against `main` at `744e3bbb`, naming the pull request that shipped each. Tracked by
[#1217](https://github.com/mihazs/lazysh/issues/1217), under the Agent view epic
[#1119](https://github.com/mihazs/lazysh/issues/1119). The design the gaps are measured
against is the [Agent view specification](../agent-view.md); this page does not change it.

The Agent view should show what the agent's own screen shows, as it happens, and be at least
as good to read on a phone as the best mobile agent clients. This page lists every kind of
screen element the Claude Code and Codex terminal UIs show, where each is recorded, how the
reference apps present it, what the Agent view does today, and which issue closes the gap.

## How the inventory was made

- **Agent screens**: the public documentation of each agent ([Claude Code interactive mode and
  status line](https://code.claude.com/docs/en/interactive-mode), [Codex CLI](https://learn.chatgpt.com/docs/codex/cli)),
  combined with the record **types** present in locally stored Claude Code and Codex session
  files, to learn which elements leave a trace in a transcript at all. Only type names were
  read. No prompt, path, output or other session content appears in this page, in the issues
  or in any test; fixtures for every gap are synthetic.
- **Reference apps**: public material only, collected in the two reference studies on the
  umbrella issue ([part 1, Herdr mobile clients](https://github.com/mihazs/lazysh/issues/1217#issuecomment-6798068186),
  [part 2, Claude, Codex, Perplexity, Grok, GitHub Copilot, Cursor and Happy](https://github.com/mihazs/lazysh/issues/1217#issuecomment-6798518905)).
  Behaviour is described in our own words; nothing was copied. "n/d" means not documented
  publicly, not absent.
- **Agent view today**: the client code on `main` (`AgentView.tsx`, `ChatPanel.tsx`,
  `ChatInteraction.tsx`, `chatInjected.ts`) and the companion's conversation readers.
- Transcript formats are the agents' own and not a public contract. The adapters tolerate
  record types they do not know, and each new element ships only with synthetic fixtures for
  the shapes it relies on.

Status words: **shipped** (works on `main`), **partial** (part exists, the cell says what is
missing), **missing**, **in flight** (a PR is open). Gap numbers are GitHub issues.

Not a gap: **token streaming**. Claude Code and Codex record completed items, so no client
that wraps them shows partial text, and lazysh does not promise it. "Real time" here means a
completed record on screen within a fraction of a second, plus a visible working state.
Agents with a live protocol (the Codex app-server daemon) are the exception the spec
already describes under [#1124](https://github.com/mihazs/lazysh/issues/1124).

## Where the elements come from

The sources and authority order of the [Agent view specification](../agent-view.md#sources-and-authority)
apply unchanged: a live protocol outranks the transcript, the transcript outranks hooks, and
the terminal screen is used only for what nothing above shows and never grants authority.
The working state, the waiting state and the model and mode each name their source in the
view, because the apps studied show that a state taken from the wrong source is the most
common way a mobile client misleads (a turn shown finished while it runs, "ready for review"
with background work, a send arrow stuck disabled).

### Fallback for unmapped records and per-adapter coverage

Tracked by [#2089](https://github.com/mihazs/lazysh/issues/2089). A record the adapter does not map must not vanish, so the Agent view shows it as a muted
**Not shown natively** line (the `unmapped` event kind, see [the companion](../companion.md)) whose label is the record's own type, or `system/<subtype>`, and
that opens to the agent's own text. Known housekeeping stays hidden: `queue-operation`, `permission-mode`, `cost-state`, `worktree-state`,
`file-history-snapshot`, `summary`, titles and tags, and the `system` subtypes `turn_duration`, `compact_boundary`, `stop_hook_summary`, `local_command` and `api_error`.
A `system` record needs text to show; a record without a `uuid` cannot sit on the active branch and is not shown. The table is the checklist for the
remaining parity work: a row turns into mapped elements, issue by issue, and an adapter without a fallback is a gap.

### Records-only adapters

The agents that have no conversation view here show one of two things for a pane that reports a session, and neither has a composer. GitHub Copilot CLI,
Kimi CLI and Droid have records whose path names the session the hook reports (the session directory, or the UUID file name), so the view reads those
records, read-only, under a partial label ([#1658](https://github.com/mihazs/lazysh/issues/1658)). It shows the turns the adapter's reader keeps (text, tool calls and
results; Kimi and Droid omit what their own formats do not record, see [the companion](../companion.md)), the hook state in the header and **Show terminal**, and reads on
from the cursor every 5 seconds. Pi, OMP and Hermes have no hook setup, Cursor's records are the IDE's export, Amp's an explicit JSON export, and Grok Build reports
nothing, so none has a session the records could be tied to: the view shows the last reported state, labelled as state only, with **Show terminal**. Not run against a real Copilot CLI, Kimi CLI or Droid.

### OpenCode input

OpenCode's prompt box was checked on 2.2.7 in a real tmux pane (an isolated profile, one short prompt to its free model). The confirmed `send` writes a short prompt as one burst of keys (`send-keys -H`) and presses Enter; the box drops such a burst, so the send would have reported a prompt as delivered that never arrived. Characters typed one at a time reach it, and so does a bracketed paste (`paste-buffer -p`, the way `send_long` writes a prompt over 4 KiB) followed by a raw Enter, which submits it. The key profile for OpenCode is therefore: every prompt is one paste then Enter (`pasted` in `tmux_chat.rs`; the client still sends `send` or `send_long` by size), and Stop is two Escapes about 0.4 s apart as separate sends (one `send-keys Escape Escape` is read as one key and interrupts nothing; one Escape shows "esc again to interrupt"; two on an idle prompt leave the typed text alone). The Agent view sends to OpenCode on tmux only, offers no slash palette, no `!` or `#` mode name and no `@` file picker for it (nothing here has checked what they mean in its prompt), and no permission-mode switch. The transcript session for a pane is the database session id its hook reports.

## Work tracking per agent

Tracked by [#1285](https://github.com/mihazs/lazysh/issues/1285). Each cell is what the agent records and what lazysh
reads from it; "not mapped" means lazysh does not read that record, either because it was not verified or because the work
is not done yet. Nothing is guessed: the element is absent, or an ordinary tool block. The mapping table itself
lives in the companion (`apps/agent/src/transcript/interaction.rs` for plans and questions, `work.rs`, `opencode_work.rs`,
`grok_work.rs` and `gemini_conversation.rs` for work items, `grok_conversation.rs` for a Grok Build edit).

| Element | Claude Code | Codex | OpenCode | Gemini CLI | Grok Build |
| --- | --- | --- | --- | --- | --- |
| Plan or todo list | `TodoWrite` | `update_plan` | `todowrite` | `write_todos` (also `blocked`) | ACP `plan` updates (each replaces the whole plan) read as the shared plan card ([#1576](https://github.com/mihazs/lazysh/pull/1576)) |
| Sub-agent | `Agent` or `Task` calls | `SubAgentActivity` items | `task` calls (V1 and V2) | `invoke_agent` calls | `subagent_spawned` and `subagent_finished` records |
| Background job | `Bash` with `run_in_background`, `Monitor` | Background terminals: not recorded while they run (an item is written when the command ends), so none is listed | A background `task` only | `run_shell_command` with `is_background` (no recorded end: the default `silent` setting writes none) | `task_backgrounded` and `task_completed` records (a command or a monitor) |
| File edit as a diff | `Edit`, `Write` | `apply_patch` (`FileChange` items) | `edit` and `apply_patch` tool calls; the `patch` part lists file names only and shows nothing | `replace`, `write_file` | A completed `edit`-kind call whose output is exactly one ACP `diff` part; any other shape stays an ordinary tool block |
| Compaction, goal, retry events | `compact_boundary` and others | `compacted`, `thread_goal_updated` | `compaction` parts and V2 messages; `retry` is never recorded | `info` messages are not compression notices: nothing to map | No verified record shape: not mapped |

What the cells that stay unmapped rest on ([#1847](https://github.com/mihazs/lazysh/issues/1847)). Grok Build and Gemini CLI
are not installed on the development host and no account exists to run them, so no session of either was captured. The Grok
Build cells are read from the official writer source at the commit the Grok fixtures already pin (`2bdd1d6a`), which
serializes `subagent_spawned`, `subagent_finished`, `task_backgrounded` and `task_completed` into the session's
`updates.jsonl` (and reads the two `task_*` lines back itself when it reloads a session), and builds an edit's ACP `diff`
part; `apps/agent/tests/fixtures/grok-acp/README.md` lists the files. A Grok record of those kinds with another shape, an end
naming no launch and a task with no recorded end change nothing, so a job with no end stays running. For Gemini CLI, the
released 0.68.0 package and the current source write an `info` message only for binary tool output (an image a tool
returned), never for a compression, so the compression notice is not in the session file. A finished background shell
records nothing under the default `backgroundCompletionBehavior` of `silent`; `inject` and `notify` fold a
`[Background command completed ...]` text into the next turn in a shape nobody captured, so no end is read from it. For
OpenCode, 2.x keeps a retry as transient state on the assistant message (`session.retry.scheduled` sets it, the next
progress clears it); the `retry` part type exists only in the schema, no writer was found, and the host database (100,602
messages, about 700,000 parts) holds no `retry` record of any kind. None of this is a capture: re-run the check when a real
session of one of these agents shows the record.
